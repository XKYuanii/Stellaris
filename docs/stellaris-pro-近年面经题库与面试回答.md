### 1.2 从样本中归纳出的项目拷打顺序

面试官通常按下面的链条连续追问：

```text
项目介绍
  → 为什么高并发下不会超卖
  → Redis/Lua 成功后下游失败怎么办
  → MQ 丢失、重复、积压怎么办
  → 支付与超时取消同时发生怎么办
  → Redis 和数据库不一致怎么发现、恢复
  → Redis 或 MQ 整体宕机怎么办
  → 数据量继续增长怎么分片、扩容、迁移
  → 你怎么压测、监控并证明优化有效
```

所以本题库不按 Redis、Kafka 的孤立八股排序，而按业务故障传播顺序排序。

## 2. 面试前必须统一的“源码事实”

下面这些边界必须诚实表达。把优化方案说成已经落地，会被源码追问击穿。

| 主题 | 当前仓库事实 | 面试时的准确说法 |
| --- | --- | --- |
| Redis 部署 | `application.yml` 是单机 host/port 配置 | 当前验证环境是单机；集群化需要给多 Key Lua 统一 Hash Tag |
| Lua 原子性 | 校验、扣余票、迁移座位、写流水在一个脚本内 | 能保证单 Redis 实例内命令不可插入；不等于 Redis 宕机后数据绝不丢 |
| Kafka 生产 | `retries: 1`，未显式配置 `acks`；通过回调判断发送结果 | 已等生产回调，但可靠参数不完整，且 `CountDownLatch.await()` 没有超时 |
| Kafka 消费 | `enable-auto-commit: true`；业务异常被捕获后写 `DISCARD_ORDER` | 当前不是严格的“业务成功后手动提交 offset”方案 |
| Kafka 幂等 | 订单号防重注解、创建前查询、订单号唯一索引 | 有业务幂等防线，但创建订单 Kafka 没接入完整生产/消费消息记录闭环 |
| 延迟取消 | Redisson `RDelayedQueue` + 生产/消费记录 + 定时对账重发 | 闭环主要覆盖延迟取消消息，不要泛化成所有 Kafka 消息都已可靠对账 |
| 库存对账 | 对账实现存在 | `ReconciliationTask` 的 `@Scheduled` 当前被注释，不能说正在自动周期执行 |
| Sentinel | 有配置类源码 | 类上没有明显 `@Configuration`，也未检索到显式导入；不能说规则已完整生效和持久化 |
| 虚拟分片 | SQL 有 `d_sharding_route_mapping`，订单服务有实体 | 当前实际订单路由仍是固定基因位算法，未发现映射表接入路由算法 |
| 迁移服务 | Hint 强制路由、游标分批、dry-run、限速 | 目前主要迁移 `d_order`；子表、双写、断点状态、原子切换仍需完善 |
| 压测 | 仓库有项目方 JMeter 报告 | 能复述报告，但不能冒充自己实测；最好亲自复现并记录环境 |

# 第一部分：项目全局认知

## Q01 `[P0]` 请介绍一下这个项目

**先理解**

面试官不是要听技术名词清单，而是要确认你能否用“业务矛盾—系统方案—结果边界”讲清项目。

**项目落点**

- 服务：Gateway、用户、节目、订单、支付、自定义治理、后台、迁移。
- 主入口：`ProgramOrderController` → `ProgramOrderContext` → `ProgramOrderV4Strategy`。
- 核心：`ProgramOrderService`、`programDataCreateOrderResolution.lua`、`CreateOrderConsumer`、`OrderService`。

**面试回答**

> stellaris-platform 是一个演出票务高并发微服务项目，核心矛盾是热门演出开票时，大量用户同时竞争有限票档和具体座位。系统既要避免超卖、同座重复占用和重复下单，又要缩短同步请求链路，并保证 Redis 库存、节目数据库、订单状态最终一致。
>
> 请求先经过 Gateway 做 RSA 验签、JWT 登录态解析和基于 Redis Lua 的接口频控。V4 下单链路在节目服务完成用户、票档、限购等组合校验，再按用户和节目防重复执行，并用节目加票档粒度的本地锁降低同 JVM 竞争。真正的库存正确性由 Redis Lua 保证：一次完成余票检查、手选或自动配座、扣减余票、座位从未售迁到锁定、写库存流水。
>
> Redis 预扣成功后，系统预生成带用户基因的订单号，把订单快照发到 Kafka；订单服务消费后更新节目数据库库存并创建订单。未支付订单通过 Redisson 延迟队列取消，支付成功则把锁定座位变成已售。项目还实现了库存流水对账、异常订单集合、消息生产消费记录、分库分表和迁移服务。
>
> 我会把它概括为：用 Lua 保证并发原子性，用 Kafka 削峰，用幂等、状态锁、流水和对账处理异步系统的不确定性。当前代码仍有生产化边界，例如 Kafka 自动提交 offset、对账调度开关未启用、Redis Cluster 同槽约束未改造，这些也是我重点分析的改进方向。

**追问**

- 为什么“返回订单号”不等于“订单已经落库”？
- Redis 预扣和数据库扣减为什么都需要？
- 你本人具体验证或改造了什么？不要把原作者工作说成自己的。

## Q02 `[P0]` 你认为项目最大的技术难点是什么

**先理解**

难点不是“用了很多中间件”，而是多个系统之间没有共同事务：Redis 成功、Kafka 失败、数据库失败、支付回调迟到都可能产生中间状态。

**面试回答**

> 最大难点是高并发库存正确性和跨 Redis、Kafka、MySQL 的最终一致性。单点看，Lua 可以防止两个请求同时扣到同一份库存；但 Lua 成功以后，Kafka 发送、消费者落库、支付和关单仍可能失败，所以仅说“Lua 防超卖”是不完整的。
>
> 项目的处理思路是分层：第一层用 Lua 把库存判断、扣减、锁座和写流水做成原子操作；第二层用订单号、防重注解和唯一索引让异步消费幂等；第三层对发送失败即时回滚，对消费失败写入 `DISCARD_ORDER`；第四层用 Redis 流水和数据库订单流水对账，发现缺失并补偿；第五层支付和关单使用相同订单号的分布式锁串行化状态迁移。
>
> 真正需要继续加强的是可靠事件闭环：创建订单 Kafka 应改成生产记录或本地消息表、生产端 `acks=all`、消费端手动提交、失败重试和死信队列，并启用和监控库存对账调度。

## Q03 `[P0]` 从用户点击购票到支付完成，完整链路是什么

**先理解**

要按“同步链路、异步链路、超时链路”分开讲，避免把执行时间线说乱。

**面试回答**

> 同步链路是：请求过 Gateway 验签、鉴权和限流；节目服务选择 V4 策略；组合校验用户、节目、场次、票档、购票人和限购；`@RepeatExecuteLimit` 防重复提交；本地细粒度锁减少 Redis 竞争；Lua 原子扣库存、锁座并写 `reduce` 流水；随后生成订单号并发送 Kafka，等生产者回调成功后向前端返回订单号。
>
> 异步链路是：`CreateOrderConsumer` 消费消息，先判断是否超过五秒，正常时调用 `OrderService.createMq()`；它先调用节目服务更新 MySQL 票档和座位，再在订单库事务内写主订单、购票人订单、记录流水和订单节目关联。前端可以通过短期 `ORDER_MQ` 缓存或订单查询确认是否真正创建。
>
> 结束链路有两条：支付成功时，支付宝回调经过订单号锁，把订单改为已支付，座位从锁定迁到已售；超时未支付时，Redisson 延迟队列触发取消，把订单改为取消，座位回到未售并回补库存。如果关单后支付回调才到，系统走退款逻辑。

## Q04 `[P1]` V1、V2、V3、V4 为什么逐步演进

**先理解**

版本演进要回答“每版消除了哪个瓶颈”，不能只背编号。

**面试回答**

> V1 更接近直接按业务步骤查询和扣减，逻辑清晰但并发窗口大；V2 引入本地锁，把同实例内节目票档竞争串行化，但多实例之间本地锁不能保证全局正确性；V3 把库存校验、扣减和锁座放入 Redis Lua，正确性从 Java 锁转移到 Redis 的原子脚本；V4 在 V3 的基础上把订单数据库落库放到 Kafka 消费端，缩短入口同步链路并削峰。
>
> 所以本地锁是减压手段，Lua 是库存正确性手段，Kafka 是时延和削峰手段，三者解决的不是同一个问题。V4 的代价是系统从同步成功变成异步受理，需要增加结果查询、消息可靠性、幂等、对账和补偿。

## Q05 `[P1]` 为什么拆成节目、订单、支付、用户等服务

**先理解**

服务拆分要看领域边界和独立扩缩容需求，不是为了把代码分成更多进程。

**面试回答**

> 拆分依据是领域职责和扩缩容特征。节目服务承受开票时的热点读和库存竞争；订单服务承担写入、状态流转和用户订单查询；支付服务隔离第三方支付通道及账单；用户服务管理登录和实名购票人；Gateway 统一安全与流量治理。这样热门开票时可以优先扩容节目和订单服务，也避免支付或用户服务故障直接拖垮全部逻辑。
>
> 代价是本地事务变成跨服务一致性问题、调用链更长、排障更难，所以项目才需要 Feign 上下文传递、traceId、消息、幂等、补偿和监控。微服务不是越多越好；如果规模很小，模块化单体可能成本更低。

# 第二部分：高并发库存与 Redis Lua

## Q07 `[P0]` 什么是超卖、少卖和一人多单

**先理解**

- 超卖：成功售出的数量大于真实库存，属于正确性事故。
- 少卖：库存实际还有，但系统因脏锁、消息失败或回补失败显示售罄，属于可用性和收入损失。
- 一人多单：同一用户绕过限购重复成功，不一定导致总库存负数，但破坏业务规则。

**面试回答**

> 项目分别处理三类问题。超卖和同座重复占用由 Lua 的库存判断、扣减和座位迁移原子性控制；一人重复提交由 `@RepeatExecuteLimit` 以 userId+programId 组成幂等键，并结合订单号唯一性兜底；少卖主要依靠发送失败回滚、延迟取消回补、异常订单集合和库存流水对账发现与恢复。

## Q08 `[P0]` 为什么库存既放 Redis 又放 MySQL

**先理解**

Redis 解决高并发决策速度，MySQL 承担持久化业务事实，两者的职责不同。

**面试回答**

> Redis 和 MySQL承担不同职责。Redis 是高并发竞争入口，利用内存性能和 Lua 原子性快速决定谁拿到票；MySQL 是持久化事实和审计基础，保存票档、座位、订单及流水，支持 Redis 丢数据后的重建和对账。
>
> 正常链路先在 Redis 预扣，Kafka 消费后再更新节目数据库。这样数据库不直接承受开票瞬间的全部竞争，但系统接受一个短暂的不一致窗口。因此必须有失败回滚、幂等和对账，不能把 Redis 当成唯一事实来源，也不能只扣 Redis 永远不落库。

## Q09 `[P0]` Redis 单命令是原子的，为什么还需要 Lua

**先理解**

单命令原子不代表“先查再改”的多步业务是原子的，并发问题就出在步骤之间。

**面试回答**

> 单条 `HINCRBY` 是原子的，但下单不是一个命令，而是“查余票—判断—校验指定座位或自动配座—扣多个票档—迁移多个座位—写流水”。如果由 Java 发多条命令，两个请求会在命令之间交叉执行，都基于旧库存做决定。
>
> Lua 在 Redis 线程中把整段逻辑作为不可被其他命令插入的执行单元。项目的脚本先完成全部票档和座位校验，再统一 `HINCRBY`、`HDEL`、`HMSET` 和 `HSET`，从而消除检查到写入之间的竞争窗口。

## Q10 `[P0]` Lua 脚本的执行顺序是什么，为什么先全部校验再写

**先理解**

Redis 保证脚本执行期间不被插入，但不会像数据库事务一样在运行错误后自动回滚已执行命令。

**面试回答**

> 脚本先区分手动选座和自动配座；再读取所有票档余量，任一不足就返回；手选模式逐座位检查是否仍在未售 Hash、状态和价格是否合法，自动模式从未售座位中排序寻找同排连续座；所有条件通过后才扣余票、从未售 Hash 删除座位、写入锁定 Hash，最后用 Redis `TIME` 写库存流水并返回实际锁定座位。
>
> 先校验后写很重要，因为 Redis Lua 虽然执行期间不可插入，但并不提供传统数据库那样的运行时错误自动回滚。若一边校验一边修改，后面的票档失败时，前面已经改过的数据可能留下半成功状态。

## Q11 `[P0]` 两个人同时手选同一个座位，为什么只有一个成功

**先理解**

同座位竞争的关键不是先到先得的口号，而是检查和状态迁移必须不可分割。

**面试回答**

> 两个请求都进入同一 Redis 实例后，脚本仍是串行执行。第一个脚本从未售 Hash 读到 seatId，校验成功后在同一次执行中 `HDEL` 未售座位并写入锁定 Hash。第二个脚本开始时，这个 seatId 已不在未售 Hash，直接返回座位不可用。因此正确性来自“读取并迁移状态”在一个脚本内，而不是客户端先查再锁。

## Q12 `[P1]` 自动配座为什么放 Lua，性能风险是什么

**先理解**

把算法放入 Lua 能保证选中和锁定的原子性，但 Redis 单线程执行长脚本会阻塞其他请求。

**面试回答**

> 放在 Lua 中是为了避免 Java 先选出座位、再写 Redis 之间的竞争窗口。脚本读取当前未售座位，按排和列排序，找到连续座位后立即迁移状态，选座结果不会在写入前被别人抢走。
>
> 风险是脚本使用 `HVALS` 全量读取票档座位，再 JSON 解码和排序，复杂度和阻塞时间会随座位数增长。Redis 执行 Lua 时其他命令不能插入，长脚本会放大热点 Key 延迟。生产优化可以按区域或排拆分座位池、预计算连续座位块、限制单次候选集，或让 Redis 只完成候选座位的最终原子确认。

## Q13 `[P0]` Lua 执行到一半 Redis 节点宕机会怎样

**先理解**

“原子性”回答的是并发可见性，不等于硬件故障下的持久性；并且要把“Redis 的机制”和“这个项目实际补到了什么程度”分开说。

**面试回答**

> 第一，正常运行时 Lua 对其他 Redis 命令是原子的：脚本没结束，别的客户端不会插进来，也看不到“扣了一张票、座位还没锁”的中间状态。它不是数据库事务，没有 undo log；若脚本中前面的写已经成功、后面的业务命令报错，Redis 不会自动把前面的写回滚。
>
> 第二，Redis 5 以后默认采用 effects replication：脚本执行时先收集写命令，脚本完整结束后，再把这些命令作为一个 `MULTI/EXEC` 传播给副本和 AOF。因此主节点真的在脚本执行到一半就挂掉时，发生故障转移的新主通常拿到的是脚本执行前的副本数据，而不是“半套脚本同步过去”的数据。但脚本已经执行完、只是复制或落盘尚未完成时，仍可能有“客户端已收到成功，新主没有这次写”的窗口。
>
> 落到本项目，不能说“Redis 挂了会自动全量恢复”。Lua 在 `ProgramOrderService` 里完成扣余票、锁座，并写入 `PROGRAM_RECORD` 流水；随后异步创建 `ProgramRecordTask`，再发送 Kafka 创建订单。订单已经落库、但 Redis 流水缺失的场景，`OrderTaskService.reconciliationTask` 会拿数据库未对账的订单明细与 `PROGRAM_RECORD` 比较，按流水反推余票，删除相关座位/余票缓存让其重新加载，并把记录标为已对账。这是**局部对账补偿**。
>
> 但它不是 Redis 整库宕机后的自动重建：全量对账的 `@Scheduled` 目前被注释，现有入口是 `/reconciliation/task` 和 `/reconciliation/task/all` 手工触发；而且若 Lua 刚成功就宕机，订单、Kafka 消息和数据库对账明细都还未来得及写入，这套对账没有数据库依据可补。因此我会如实说：当前仓库已实现“有订单明细后的库存流水补偿”，没有完成“任意宕机窗口下的全量自动恢复”。生产上需要把对账任务启用，并补一条按数据库订单/座位状态重建 Redis 缓存的全量恢复流程。

## Q14 `[P0]` 这段多 Key Lua 在 Redis Cluster 能直接运行吗

**先理解**

Cluster 中脚本能否执行取决于所有实际访问的 key 是否落在同一 hash slot。

**面试回答**

> 不能直接承诺。Redis Cluster 要求一次脚本访问的所有 Key 位于同一个 Hash Slot，通常给同一业务聚合的 Key 加相同 Hash Tag，例如 `program:{programId}:remain`、`program:{programId}:seat:lock:{ticketCategoryId}`。当前项目 Key 没有 `{}`，脚本还通过模板动态拼接多个 Key，配置也是单机 Redis。
>
> 集群化时我会让同一节目下脚本所需 Key 使用相同 `{programId}`，并把真实 Key 全部通过 `KEYS` 显式传入；如果一笔订单允许跨节目，就必须拆成多个同槽原子操作，再在业务层处理跨槽一致性。

## Q15 `[P0]` Lua 已经保证正确性，为什么还要本地锁

**先理解**

要分清“正确性保障”和“减少竞争的性能优化”，本地锁在多实例下不能替代 Lua。

**面试回答**

> 两者目的不同。Lua 是最终正确性边界；本地锁只在单实例内把相同节目票档的请求适度串行化，减少大量失败请求同时访问 Redis、网络往返和长脚本竞争。多实例之间本地锁互不感知，因此绝不能把它当成防超卖的唯一手段。
>
> V4 通过 `BaseProgramOrder.localLockCreateOrder` 以节目和票档生成细粒度锁，多票档按固定顺序获取并逆序释放，降低死锁风险。热点极高时还应在网关限流、排队令牌和热点隔离层继续削峰。

## Q16 `[P1]` 多票档加多把锁，如何避免死锁

**先理解**

死锁的根因是不同请求以不同顺序持有并等待多个资源，统一加锁顺序能破坏环路等待。

**面试回答**

> 死锁常来自两个请求以不同顺序拿相同的多把锁，例如请求 A 先票档1后票档2，请求 B 先票档2后票档1。解决方式是对票档 ID 排序，所有请求按相同全序获取，释放时逆序。这样不会形成环形等待。还可以使用 `tryLock` 超时，失败后释放已持有锁并重试，避免无限等待。

## Q17 `[P1]` 热门节目形成 Redis 热点 Key，Lua 仍然会成为瓶颈，怎么办

**先理解**

Lua 解决了竞态条件，却会把同一热 key 的修改串行化；正确性和吞吐是两个问题。

**面试回答**

> Lua 能保证正确性，但不能消除单 Key 热点，因为同一节目请求仍集中到一个 Redis 节点串行执行。优化顺序应是先挡流量，再缩短脚本，最后才考虑库存分桶。
>
> 项目已有网关频控、本地票档锁和票档维度 Hash。进一步可以做预约/验证码、动态令牌、按票档或区域拆分座位池、热点节目独立 Redis 分片、脚本候选集预计算。若把同一票档库存拆成多个桶，需要额外解决桶选择、局部售罄但全局有库存、回补路由和总量对账，不能只做随机 `DECR`。

## Q18 `[P1]` Redis 缓存首次不存在，大量请求会不会一起查数据库

**先理解**

这是缓存击穿：热点数据缺失时，并发请求一起穿透到后端存储。

**面试回答**

> 项目在执行下单 Lua 前先调用座位和票档缓存初始化。`SeatService.selectSeatResolution()` 先查缓存，未命中后抢节目+票档的 Redisson 锁，进入锁后再次检查，仍为空才查 MySQL 并按未售、锁定、已售状态回填多个 Hash。这是典型的双重检查互斥重建，能把同一热点 Key 的数据库回源压成一个线程。
>
> 边界是空数据也要有防穿透策略，否则数据库确实没有座位时，每次仍可能回源；此外缓存过期时间要避免大量节目同一时刻过期。

# 第三部分：防重复、幂等与分布式锁

## Q19 `[P0]` 防重复执行和幂等是一回事吗

**先理解**

- 防重复执行：尽量不让第二次请求进入核心逻辑。
- 幂等：即使重复执行，最终业务效果仍等价于执行一次。

**面试回答**

> 两者不是一回事。防重复是入口优化，幂等是结果正确性的底线。网络超时、客户端重试、MQ 至少一次投递都可能绕过一次性的入口判断，所以关键业务必须具备幂等结果。
>
> 项目下单入口用 `@RepeatExecuteLimit` 以 userId+programId 防短时间重复提交；Kafka 消费端以 orderNumber 防重复；订单创建前查询是否已存在，订单表对 `order_number` 还有唯一索引兜底。即使两条重复消息并发通过前置查询，数据库唯一约束仍能阻止两张相同订单。

## Q20 `[P0]` `@RepeatExecuteLimit` 的实现原理是什么

**先理解**

它是用 AOP 把“按业务 key 串行执行”变成声明式能力，key 粒度直接决定隔离范围。

**面试回答**

> 切面先根据注解里的 SpEL 参数生成业务锁名，再查 Redis 成功标记；如果已经成功过，直接拒绝。未成功时先尝试本地 `ReentrantLock`，减少同 JVM 内无效的远程竞争；拿到本地锁后再抢 Redisson 公平锁，保证多实例互斥；进入分布式锁后再次检查成功标记，执行业务成功后按配置写入带过期时间的成功标记，最后逐层释放锁。
>
> 它使用了“Redis 标记 + 本地锁 + 分布式锁 + 二次检查”。但这主要是时间窗口防重，不替代数据库唯一索引和订单状态条件更新。

## Q21 `[P1]` 为什么先拿本地锁再拿分布式锁

**先理解**

分层锁的目的是先在进程内合并竞争，再让少量请求进入跨节点协调。

**面试回答**

> 同一实例内如果一百个相同请求都直接竞争 Redisson，会产生一百次网络交互和 Redis 锁竞争。本地锁先挡住同 JVM 的重复请求，只让极少线程进入分布式竞争；Redisson 再处理多实例之间的互斥。这样降低远程锁压力，但增加了实现复杂度，需要保证所有异常路径都释放本地锁。

## Q22 `[P0]` Redisson 看门狗是什么，业务一直执行锁会永远不释放吗

**先理解**

看门狗解决业务执行时间不确定时锁 TTL 过早到期，不是让死掉的客户端永久占锁。

**面试回答**

> 使用不指定固定 leaseTime 的 Redisson 锁时，默认有一个锁租约，并由看门狗周期续期，只要持锁客户端和线程仍存活，任务就会续租，避免业务未完成锁却过期。正常执行到 `finally` 会主动解锁；进程宕机后看门狗停止，锁在租约到期后自动释放，所以不会永久死锁。
>
> 但如果业务线程永久卡住且进程仍存活，看门狗可能持续续期，锁就会长期占用。因此仍要给外部 RPC、数据库和任务本身设置超时，监控锁持有时长；已知最大执行时间的短任务也可以评估固定租约，但必须防止租约小于业务时间导致锁提前失效。

## Q23 `[P1]` Redis 主从切换时分布式锁会不会失效

**先理解**

如果锁写入还未复制到从库主节点就宕机，新主可能看不到这把锁。

**面试回答**

> 可能。客户端在旧主节点加锁成功，如果锁记录还未复制到从节点旧主就宕机，从节点提升为新主后，另一个客户端可能再次拿到同名锁，出现两个持锁者。Redisson 的可重入和看门狗解决的是客户端锁语义，不自动消除异步复制窗口。
>
> 对绝对不能并发执行的资金或唯一写操作，不能只依赖缓存锁，还应有数据库状态机、唯一约束、版本号或 fencing token 兜底。项目订单状态同时有订单号锁和状态检查，但若要进一步严谨，应使用 `WHERE order_status = NO_PAY` 的条件更新，让数据库成为最终裁决者。

## Q24 `[P1]` 公平锁和普通可重入锁如何选择

**先理解**

公平性主要解决长期饥饿，代价是维护等待顺序和更低吞吐，不等于业务上绝对先到先得。

**面试回答**

> 公平锁尽量按等待顺序获取，减少饥饿，但需要维护排队信息，吞吐和延迟通常不如非公平锁。项目防重复切面使用公平锁，强调同一业务键的有序竞争；普通业务状态锁使用可重入锁，支付回调内部可能再次进入同订单状态逻辑，可重入能避免同线程重复加锁自锁。
>
> 抢票核心正确性并不依赖“先来先得”的 Java 锁公平性，最终顺序仍由请求到达 Redis 和脚本执行顺序决定。

## Q25 `[P1]` 为什么订单号唯一索引仍然必要

**先理解**

应用层防重都可能因超时、重试或并发穿透，数据库约束是最终不变式。

**面试回答**

> 应用层的“先查再插”不是原子的：两个重复消费者可能同时查到不存在，然后都插入。唯一索引由数据库在最终写入点保证一个 orderNumber 只能成功一次，是并发竞态的最后防线。捕获唯一键冲突时应把它识别为幂等重复，而不是无限重试。

## Q26 `[P2]` 一人一单只按 userId+programId 防重够吗

**先理解**

幂等 key 必须匹配真实业务规则；“一人”、“一单”和“一场次”的定义不清会导致误杀或漏防。

**面试回答**

> 要看业务规则。如果一个用户对同一节目永远只能有一张订单，userId+programId 可以；如果允许取消后重买、多个场次或每单多张票，就需要把场次、活动批次、幂等请求号或订单状态加入规则。当前注解是时间窗口防重复，同时项目还有限购数量校验和 `ACCOUNT_ORDER_COUNT`。生产上应由明确的业务唯一键或限购计数 Lua 原子判断，而不是把所有场景都压成永久的一人一单。

# 第四部分：Kafka 异步创建订单

## Q27 `[P0]` 为什么要用 Kafka 异步创建订单

**先理解**

异步不是让总工作量消失，而是改变用户请求的完成点，并用队列吸收突发流量。

**面试回答**

> 同步创建需要在请求线程里跨服务更新节目数据库并写订单主表、购票人表和流水，数据库抖动会直接拉长接口时间。V4 让同步请求只完成校验、Redis 预扣和 Kafka 发送确认，真正落库由消费者按可控速度处理，实现削峰和故障隔离。
>
> 代价是接口返回的只是“已受理”的订单号，不代表订单已落库。前端要查询创建结果，后端要处理消息丢失、重复、延迟、积压和消费失败，并通过幂等、重试、异常订单和对账保证最终一致。

## Q28 `[P0]` V4 返回订单号时，订单到底创建成功了吗

**先理解**

异步架构必须区分“系统已受理”和“业务结果已持久化”两种成功。

**面试回答**

> 还不能说正式订单已经创建成功。`createOrderByMq()` 只等待 `KafkaTemplate.send()` 的成功或失败回调；回调成功表示生产者已按当前配置得到 Kafka 确认，消费者可能尚未处理。订单号在发送前已经生成，所以可以先返回给前端。
>
> 项目消费者创建完成后写一个一分钟的 `ORDER_MQ` 缓存，前端可轮询确认。更完整的接口语义应返回“排队中/受理成功”，并提供订单状态查询或 WebSocket 通知，避免用户把受理误解成出票成功。

## Q29 `[P1]` Kafka 为什么吞吐高

**先理解**

Kafka 的吞吐来自顺序追加、批处理、页缓存和分区并行等系统性组合，不是单一黑科技。

**面试回答**

> 核心原因包括分区并行、追加顺序写日志、充分利用操作系统 Page Cache、生产和消费批量处理、压缩，以及网络传输的零拷贝优化。不能回答“Kafka 完全在内存里”，它的日志仍然持久化到磁盘。项目选择 Kafka 更看重开票突发流量下的吞吐和分区扩展能力。

## Q30 `[P1]` Kafka 如何分区，项目应使用什么消息 Key

**先理解**

消息 key 同时影响同 key 有序性、分区负载均衡和故障热点，应由业务有序边界决定。

**面试回答**

> 未指定 Key 时，生产者通常按黏性分区等策略分配，不能保证同一业务实体始终进入同一分区。Kafka 只保证单分区内有序，不保证 Topic 全局有序。
>
> 订单状态事件如果存在创建、支付、取消的先后依赖，应使用 `orderNumber` 作为消息 Key，让同一订单进入同一分区，同时不同订单仍可并行。当前 `CreateOrderSend` 只发送 topic 和 value，没有显式 Key，这是可以改进的地方。

## Q31 `[P0]` Kafka 生产端如何保证消息不丢，当前项目做到了什么

**先理解**

生产可靠性是“业务事件已产生”到“Broker 已可靠接收”的全链路，不是只调一次 `send()`。

**面试回答**

> 生产端可靠性通常需要：业务事件先有可恢复记录；生产者开启幂等，设置 `acks=all` 和合理重试；Broker 配置多副本和 `min.insync.replicas`；发送失败可重投并有告警。
>
> 当前项目的已实现部分是 `KafkaTemplate.send()` 回调和 `retries: 1`，发送失败会回滚 Redis 锁座；但没有显式 `acks=all`，也没有给创建订单 Kafka 建可靠消息记录，而且等待回调用的是无超时 `latch.await()`。更稳健的改造是 Redis 预扣后写可靠事件/操作流水，由后台投递器发送，生产回调更新事件状态；等待设置超时，超时不能盲目回滚，而要先查询或由对账判定消息是否实际入队。

## Q32 `[P0]` 为什么发送超时不能直接认定 Kafka 失败并回滚库存

**先理解**

分布式调用常见“结果未知”：Broker 可能已写成功，只是响应丢了。

**面试回答**

> 超时只表示生产者没有按时拿到结果，不等于 Broker 一定没收到。如果此时直接回滚库存，而原消息稍后被消费者创建订单，就会出现订单成功但库存已释放，造成超卖风险。
>
> 正确做法是给消息分配唯一事件 ID，生产端开启幂等，超时进入“发送结果未知”状态，由可靠事件表查询/重投；消费者按事件 ID 或订单号幂等。只有确认事件最终未被处理时才补偿库存。当前项目成功或失败回调路径明确，但无界等待也正是为了回避这个未知状态，生产化需要显式建模而不是无限等。

## Q33 `[P0]` 消费端如何防止消息丢失，当前自动提交有什么风险

**先理解**

offset 表示消费进度，若它先于业务成功提交，客户端宕机后就可能跳过未完成的消息。

**面试回答**

> 推荐在业务事务成功后手动提交 offset；业务失败则抛出异常进入重试，超过次数进死信队列并告警。否则 offset 先提交或定时自动提交后应用宕机，消息可能被标记已消费但订单没有创建。
>
> 当前订单服务配置 `enable-auto-commit: true`，消费者还捕获业务异常并写 `DISCARD_ORDER` 后正常返回，因此 Kafka 不会自然重试这条消息。项目靠异常订单集合做后续补偿，但严格可靠性更适合改为手动 ack、数据库事务成功后提交，并给可恢复和不可恢复错误设计不同重试策略。

## Q34 `[P0]` Kafka 重复消费怎么处理

**先理解**

可靠消息通常选择至少一次，所以消费者必须把重复当成正常输入并保证幂等。

**面试回答**

> Kafka 常见语义是至少一次，消费者处理成功但 offset 提交失败、重平衡或生产重试都可能带来重复。不能追求“永远不重复投递”，而应让业务幂等。
>
> 项目以 `orderNumber` 为幂等键：`createMq()` 上有防重复注解，`doCreate()` 先查订单是否存在，订单物理表还有订单号唯一索引。更严谨时把消费事件 ID 写入去重表，并让“插入消费记录”和“创建订单”在同一数据库本地事务中完成；只有事务成功才提交 offset。

## Q35 `[P0]` Redis 扣减成功但 Kafka 发送失败怎么办

**先理解**

这是跨 Redis 和 Kafka 的部分成功：两者没有共同本地事务，必须通过可重试事件或补偿收敛。

**面试回答**

> 当前失败回调把 Lua 返回的座位转换为 `SeatVo`，再通过反向 Lua 把座位从锁定 Hash 迁回未售 Hash并回补余票，随后把异常传回请求线程。
>
> 这个即时回滚只覆盖明确收到发送失败回调的情况；如果服务在 Redis 成功后、发 Kafka 前宕机，或发送结果未知，就需要库存 `reduce` 流水和对账识别孤儿预扣。补偿本身也必须幂等，不能重复 `HINCRBY` 导致库存越补越多。

## Q36 `[P0]` Kafka 已发送成功，但消费者创建订单失败怎么办

**先理解**

Broker 保存成功只说明消息可被消费，不代表下游跨服务业务已成功。

**面试回答**

> 当前消费者把超过五秒或创建异常的消息写到按 programId 组织的 `DISCARD_ORDER` Redis List，并上报 Prometheus 失败指标。后台可以根据消息里的订单、座位和 identifierId 做回滚或重建。
>
> 但这仍不是自动重试闭环：异常集合本身在 Redis，Redis 丢数据也会丢；消费端自动提交可能让 Kafka 不再投递。生产化方案应先区分临时故障和业务非法：临时故障指数退避重试，超过阈值进入持久化死信/异常表；补偿处理带幂等状态并可人工介入，同时库存流水对账作为第二条发现通道。

## Q37 `[P1]` 消息积压或消费者消费不过来怎么办

**先理解**

积压本质是持续输入速率大于有效处理速率，要先找出是容量不足还是下游故障。

**面试回答**

> 先看 consumer lag、入口发送速率、单条处理耗时和失败率，判断是突发流量、下游数据库慢还是坏消息反复阻塞。临时处置可以增加 Topic 分区和消费者实例，前提是分区数足够；扩容订单数据库连接池要谨慎，不能把压力直接放大到 MySQL。
>
> 根因优化包括批量消费和批量写、减少同步 RPC、优化索引和事务范围、按订单号分区、把不可恢复消息快速转死信。项目当前把超过五秒的创建消息直接丢入异常集合，这个阈值在积压时会把大量本可成功的订单判废，因此应把“排队延迟”和“业务过期时间”分开，并根据订单锁座截止时间决定是否还能创建。

## Q38 `[P1]` 为什么项目用 Kafka，不用 RabbitMQ 或 RocketMQ

**先理解**

消息中间件选型要根据吞吐、延迟、消息模型、团队运维和生态，不是排一个绝对高下。

**面试回答**

> Kafka 强项是高吞吐、分区扩展和日志保留，适合开票瞬时洪峰及后续事件回放；RabbitMQ 路由能力和低延迟任务队列体验较好；RocketMQ 对事务消息、延迟消息和业务型重试支持更直接。
>
> 项目异步创建订单选择 Kafka 是合理的吞吐取向，但超时关单没有复用 Kafka，而是自建 Redisson 延迟队列。如果更重视事务消息和多级延时，可评估 RocketMQ；选择不能只说性能，要结合团队运维能力、可靠语义、延迟需求和已有基础设施。

# 第五部分：延迟取消、支付与订单状态机

## Q39 `[P0]` 超时未支付订单如何自动取消

**先理解**

超时关单是一个未来时间事件，既要到期触发，又要在重启、丢消息和并发支付下保持正确。

**面试回答**

> 创建订单消息发送成功后，节目服务异步构造一条包含 messageId、traceId、programId 和 orderNumber 的延迟取消消息。发送前先在自定义服务写生产记录，再通过 `DelayQueueContext` 投递到 Redisson `RDelayedQueue`。到期后消息进入阻塞队列，订单服务的消费线程取出并调用 `OrderService.cancel()`。
>
> 取消逻辑以 orderNumber 做防重复和分布式锁，检查订单状态，更新订单与购票人订单为取消，写增加库存流水，调用节目服务释放 MySQL 座位和余票，再用 Redis Lua 把锁定座位迁回未售并回补缓存库存。消费成功或失败会更新消费记录，定时对账可发现未消费或失败消息并重发。

## Q40 `[P1]` Redisson 延迟队列底层思路是什么

**先理解**

延迟队列通常用到期时间排序，只把已到期的元素转为可消费任务。

**面试回答**

> `RDelayedQueue` 通常用按到期时间排序的数据结构保存延迟元素，并在到期后把元素转移到目标阻塞队列。项目封装层通过 `getDelayedQueue(blockingQueue)` 投递，消费者在目标 `RBlockingQueue.take()` 上阻塞等待，因此不需要业务线程轮询数据库。
>
> 它依赖 Redis 的可用性和持久化，不等同于专业 MQ 的完整确认、重试和死信能力，所以项目额外建立了消息生产/消费记录和定时对账。

## Q41 `[P1]` 延迟队列为什么分成多个隔离区

**先理解**

分区是把一个集中热点拆成可并行处理的多个独立队列，但也会增加调度和发现成本。

**面试回答**

> 单个延迟队列和单个监听线程容易成为热点。项目按 `isolationRegionCount` 创建 `topic-0...N` 多个队列，生产端轮询选择分片，每个分片各自启动监听和执行线程池，从而提高并行消费能力并缩小单队列拥塞影响。
>
> 当前选择器是进程内轮询，不保证同一订单固定分片，但取消消息彼此独立，主要依赖订单号锁保证并发安全。扩容或多实例消费时还要验证 Redisson 阻塞队列的竞争消费语义和队列命名一致性。

## Q42 `[P0]` 延迟取消消息会不会丢，项目如何补救

**先理解**

任何从业务库到队列、从队列取出到执行完成的窗口都可能丢状态，需要持久化记录对账。

**面试回答**

> 可能丢。生产记录插入成功后应用可能在真正投递前宕机；Redis 可能宕机或丢持久化数据；消费者把消息从阻塞队列取出后，提交线程池失败或进程宕机，也可能没有执行取消。
>
> 项目为延迟取消建立生产和消费记录：每分钟扫描未对账消息，未消费或消费失败时通过消息类型处理器重新投递，成功后把生产记录标成对账完成。边界是消息记录 API 和投递本身不是同一个原子事务，队列线程池拒绝后也缺少明确 requeue；因此还应以订单库扫描“到期仍 NO_PAY”的订单作为最终兜底，而不是只相信延迟消息。

## Q43 `[P0]` 支付回调和超时取消同时发生，如何避免订单又支付又取消

**先理解**

这是同一订单两个相互冲突的状态迁移，必须对同一聚合根串行决策并校验前置状态。

**面试回答**

> 两条链路都以同一个 `UPDATE_ORDER_STATUS_LOCK + orderNumber` 获取 Redisson 锁，状态检查和迁移在锁内执行，因此同一时刻只有一条能继续。先取消成功，后来的支付回调会看到 CANCEL 并触发退款；先支付成功，后来的取消会在 `checkOrderStatus()` 看到 PAY 并停止。
>
> 这是“分布式锁串行化 + 状态机检查”。更稳健的数据库兜底是条件更新：`UPDATE order SET status=? WHERE order_number=? AND status=NO_PAY`，根据影响行数判断谁赢。这样即使 Redis 锁在主从切换窗口失效，数据库仍不会让两个状态迁移都成功。

## Q44 `[P0]` 支付回调重复到达怎么保证幂等

**先理解**

第三方回调在超时未收到成功应答时会重试，因此重复是协议正常现象。

**面试回答**

> 第三方支付回调通常会重试，因此必须幂等。项目先按订单号加可重入分布式锁，再查询订单状态；已支付时状态检查拒绝重复迁移，已取消则走退款判断；只有 NO_PAY 才执行订单、购票人、座位和流水更新。
>
> 支付服务自身的账单也应以商户订单号建立唯一约束，并验证支付宝签名、商户号、金额和交易状态。向第三方返回成功前，要确保本地关键状态已经可靠落地，否则第三方停止重试后可能留下不一致。

## Q45 `[P1]` 订单取消后支付成功为什么要退款，而不是改回已支付

**先理解**

取消不只改了一个字段，通常还已释放库存和座位，再改回已支付可能造成一座多卖。

**面试回答**

> 取消时座位已经释放，可能被其他用户重新占用。如果迟到的支付回调把订单直接改回 PAY，就可能两个人拥有同一座位。因此取消是资源释放后的不可逆业务决策，迟到支付只能发起原路退款，并把订单标记为 REFUND 或退款处理中。

## Q46 `[P1]` 如何设计订单状态机

**先理解**

状态机的价值是显式列出允许的单向迁移，拒绝任意代码直接覆盖最终状态。

**面试回答**

> 核心状态包括 NO_PAY、PAY、CANCEL、REFUND。允许的主迁移是 NO_PAY→PAY、NO_PAY→CANCEL、CANCEL→REFUND；不允许 PAY 再 CANCEL，也不允许终态重复迁移。状态变更必须带前置状态条件，记录操作时间和流水，并保证订单主表、购票人订单、座位状态的业务一致。
>
> 生产上退款最好再细分 REFUNDING、REFUND_SUCCESS、REFUND_FAIL，因为调用第三方退款本身也是异步不确定过程。状态机比散落的 if 更容易审计和补偿。

## Q47 `[P1]` 延迟消息到得很晚怎么办

**先理解**

延迟消息只是提醒系统重新判断，不应把消息到达时间直接当成业务事实。

**面试回答**

> 消费时不能因为消息到达就无条件取消，而要重新查询订单当前状态和业务过期时间。已支付则幂等结束；仍未支付且确实超时才取消；若只是队列延迟但订单仍在允许支付窗口，应按业务截止时间决定。
>
> 项目取消逻辑会检查订单状态，但 Kafka 创建订单消费者用固定五秒判断消息是否丢弃，两个阈值语义不同。面试时要强调订单的支付有效期才是业务依据，队列处理延迟只是监控指标。

# 第六部分：Redis、MySQL 一致性、对账与故障恢复

## Q48 `[P0]` 项目里到底有几份库存状态，如何理解一致性

**先理解**

至少有三类相关状态：Redis 票档/座位、节目 MySQL 票档/座位、订单 MySQL 状态与流水。它们不可能靠一个本地事务同时提交。

**面试回答**

> Redis 是实时竞争视图，节目库是库存持久化视图，订单库是交易事实视图。正常顺序是 Redis 先预扣，Kafka 消费后节目库扣减并创建订单；支付或取消再同时推动订单状态、节目库座位和 Redis 座位迁移。
>
> 项目追求的不是跨三者每个瞬间都完全相同，而是关键操作不超卖、状态迁移可追踪，短暂不一致最终能通过重试和对账收敛。对账必须明确权威来源：已有正式订单流水时以数据库交易事实为准；纯缓存预扣但没有订单时要回滚缓存占用。

## Q49 `[P0]` 库存流水对账的核心原理是什么

**先理解**

对账不是定时重算一个总数，而是用同一业务标识比对两边的变更证据并定向补偿。

**面试回答**

> Lua 每次库存变化都按 `recordType_identifierId_userId` 写 Redis `PROGRAM_RECORD`，订单库同时写 `OrderTicketUserRecord`，包含相同 identifierId、用户、票档、座位和记录类型。对账任务按 programId 读取 Redis 未完成流水和数据库未对账记录，找出“数据库有、Redis 缺失”的座位记录，按 reduce、changeStatus、increase 的顺序重建变化，删除相关座位/余票缓存让它们从数据库重新加载，最后把记录迁到 `PROGRAM_RECORD_FINISH` 并更新数据库对账状态。
>
> 对账的本质不是简单比较一个总库存数字，而是用可关联的业务流水重放状态变化，这样能知道哪一笔、哪些座位出了问题。

## Q50 `[P0]` 当前库存对账是自动运行的吗

**先理解**

“有对账代码”、“调度已开启”和“线上有告警闭环”是三个不同成熟度。

**面试回答**

> 对账代码已经实现，但订单服务 `ReconciliationTask` 上的 `@Scheduled` 当前被注释，所以不能说它正在自动每三分钟执行。V4 会异步创建 `ProgramRecordTask`，但没有启用调度就不会自动触发完整处理。
>
> 我会把这视为部署开关或仓库未完成项：生产上需要启用分布式调度，给任务加防并发锁、批次游标、执行状态、失败重试和告警，并验证任务重复执行幂等。

## Q51 `[P0]` Redis 宕机时抢票系统怎么办

**先理解**

Redis 在这条链路上是并发库存的决策点，宕机后盲目绕过会丢掉防超卖前提。

**面试回答**

> 抢票正确性依赖 Redis Lua 和座位缓存，Redis 整体不可用时不应让大量请求直接降级打 MySQL，否则既可能打垮数据库，也失去原子锁座模型。更安全的策略是网关快速失败或暂停热门节目下单，只保留静态详情和查询等可降级功能；同时通过 Sentinel/Cluster 切换恢复 Redis，并限制恢复瞬间的流量。
>
> 如果业务要求极高可用，可以准备受严格限流的数据库条件更新降级链路，但它的吞吐、选座模型和一致性必须单独设计，不能简单把代码里的 Redis 调用换成查库。

## Q52 `[P0]` Redis 恢复后丢失的数据怎么恢复

**先理解**

持久化和副本只能缩小数据丢失窗口，真正恢复还需从可信业务事实重建。

**面试回答**

> 先停止或限流写入，确定恢复时间点和受影响节目；以 MySQL 票档、座位、订单状态和订单流水为权威，按节目和票档重建未售、锁定、已售 Hash 以及余票；再用未完成流水和异常订单对账，处理 Redis 成功但订单未创建的孤儿锁座；校验总座位数等于三种状态之和、余票等于未售座位数后再逐步放量。
>
> 项目已有 `SeatService` 从数据库按状态回填缓存、数据预热和删除重建入口，也有流水对账基础。不能只从 RDB/AOF 恢复后立刻开放，因为持久化快照可能比数据库状态旧。

## Q53 `[P1]` 怎么发现 Redis 库存和数据库不一致

**先理解**

最终一致不是“相信最后会一致”，而是必须能检测差异、定位原因并验证收敛。

**面试回答**

> 第一层是在线指标：按节目监控 Redis 余票、MySQL 余票、未售/锁定/已售座位数量、订单状态数和异常订单数；第二层是事件级流水对账，用 identifierId 对比 Redis 与订单数据库记录；第三层是周期全量或抽样校验，验证数量不变量。
>
> 发现差异后先冻结相关节目或标记只读，保留现场和差异详情，再执行幂等补偿。不能直接把某一边的数字覆盖另一边而不理解差异来源。

## Q54 `[P1]` 对账为什么不能永远只以数据库为准

**先理解**

事实源要按业务阶段确定：某一边可能正是本次失败中没写成功的一方。

**面试回答**

> 权威来源取决于事务阶段。正式订单和支付已经落库时，数据库是交易事实；但刚完成 Redis 预扣、订单消息尚未消费时，数据库暂时没有订单并不代表这次预扣一定错误。如果对账窗口太短，可能把正常在途消息当异常回滚。
>
> 所以要给事件状态和合理等待窗口，结合 Kafka lag、消息记录、订单号和流水判断“在途、成功、失败、未知”，而不是机械比较当前值。项目任务会查询三分钟前记录，就是为了避开正常传播延迟，但阈值仍应根据实际 P99 延迟确定。

## Q55 `[P1]` `DISCARD_ORDER` 的作用是什么

**先理解**

当同步链路无法立即安全处理失败工作时，要先把异常业务标识可靠地留下来。

**面试回答**

> 它保存 Kafka 创建订单时因消费延迟、节目库更新失败或订单创建异常而被丢弃的完整订单消息和原因，按 programId 放入 Redis List。这样后台能知道哪些 Redis 锁座没有形成正式订单，并据此回滚或人工处理，同时 Prometheus 记录失败原因指标。
>
> 边界是它仍存在 Redis 中，且当前消费者写入后就正常结束；生产上更适合把异常事件持久化到数据库或死信 Topic，建立处理状态、重试次数、最后异常和人工操作审计。

## Q56 `[P1]` 消息记录对账和库存流水对账有什么区别

**先理解**

两种对账监督的不变式不同：前者问事件是否完成传递，后者问库存变更是否两边对应。

**面试回答**

> 消息记录对账关心“某条延迟消息是否发送、是否消费、失败后是否重投”，依据 messageId 关联生产记录与消费记录；库存流水对账关心“某笔订单造成的余票和座位变化是否在 Redis 与数据库两边都有记录”，依据 identifierId、userId、recordType 关联。
>
> 前者解决消息传递可靠性，后者解决业务状态一致性。即使消息记录显示消费成功，业务状态也可能只完成一部分，所以两种对账不能互相替代。

## Q57 `[P0]` 这个项目哪些地方要求强一致，哪些接受最终一致

**先理解**

一致性等级要按业务不变式设计：竞争时的安全决策要强，跨系统副本可以有界最终一致。

**面试回答**

> 同一时刻不能把同一座位分给两个人、一次状态迁移不能同时支付和取消，这类业务不变量要在单个原子边界内强约束，项目分别用 Redis Lua 和同订单锁/状态检查实现。订单库内部写主订单、购票人和流水也使用本地事务。
>
> Redis 预扣到节目库和订单库落地、缓存与数据库同步、消息记录与业务记录之间接受短暂最终一致，因为跨服务强事务会显著放大开票链路延迟和可用性风险。接受最终一致不等于放任不一致，必须有可追踪事件、幂等重试、超时、对账、补偿和告警。

# 第七部分：Caffeine、Redis、MySQL 多级缓存

## Q58 `[P0]` 项目的三级缓存是怎么查的

**先理解**

多级缓存是用更快但容量更小、一致性更难的本地层，换取热点读延迟和 Redis 负载的降低。

**面试回答**

> 节目详情等热点读先查进程内 Caffeine，未命中时执行加载函数；加载函数再查 Redis，Redis 未命中后按节目 ID 获取 Redisson 锁并二次检查，仍没有才查 MySQL，回填 Redis 后返回，Caffeine 的线程安全 `get(key, loader)` 再把结果写入本地缓存。
>
> Caffeine 降低同实例热点访问和网络开销，Redis 让多实例共享缓存，MySQL 是最终数据源。座位链路主要是 Redis+MySQL，不应笼统说所有数据都是三级缓存。

## Q59 `[P1]` Caffeine 参数怎么设置，当前项目有什么边界

**先理解**

本地缓存参数要在命中收益、内存成本、数据新鲜度和失效风暴之间取舍。

**面试回答**

> `LocalCacheProgram` 配置 `maximumSize`，默认一万，并按节目演出时间自定义过期；创建后剩余生命周期约等于当前到演出时间，读和更新不续期。参数不能只凭经验写死，应根据单对象大小、JVM 可用堆、热点节目基数、命中率和淘汰率压测决定。
>
> 当前代码没有显式 `recordStats()`，因此不能声称已经统计 Caffeine 命中率。生产上应开启统计并监控 hitRate、evictionCount、loadFailure、loadTime，同时给不同数据类型独立容量，避免大对象挤掉真正热点。

## Q60 `[P0]` 三级缓存还会发生缓存击穿吗，怎么解决

**先理解**

多一层缓存只是降低击穿概率，并发冷启动、同时过期和主动失效仍可让各层同时 miss。

**面试回答**

> 会。多级缓存降低概率，但如果热门节目在所有实例的 Caffeine 和共享 Redis 同时失效，大量请求仍可能回源数据库。项目在本地层使用 Caffeine 原子加载合并同 JVM 请求，在 Redis 未命中层使用 Redisson 锁和二次检查合并多实例回源。
>
> 进一步可在开票前预热、给 Redis 过期时间加随机抖动、热点数据逻辑过期并异步刷新、限制回源并设置降级值。逻辑过期需要允许短暂旧数据，本项目当前主要使用物理过期，不能说已经实现逻辑过期。

## Q61 `[P0]` 本地缓存多实例如何保持一致

**先理解**

每个 JVM 有独立副本，更新一个实例不会自动修改其他实例，需要失效事件传播。

**面试回答**

> 本地缓存不共享，单实例删除不影响其他实例。项目在节目失效时先删 Redis 相关数据，再向 Redis Stream `invalid_program` 推 programId；每个节目服务实例通过广播类型消费，执行 `delLocalCache(programId)`，从而让各实例失效本地缓存。
>
> 这是最终一致方案。消息可能丢、实例离线或消费延迟，所以本地值还要有 TTL；更新事件最好带版本号，消费者只接受更高版本，并监控失败和积压。若要求严格读一致，写后读可以绕过本地缓存或按版本校验。

## Q62 `[P1]` 为什么 Redis Stream 要用广播消费，不是普通消费者组

**先理解**

缓存失效事件的目标是每个实例都执行一次，而普通消费者组是让组内任一实例处理一次。

**面试回答**

> 缓存失效事件要求每个应用实例都删除自己的本地缓存。如果多个实例属于普通竞争消费组，一条消息只由其中一个实例处理，其他实例仍保留旧值。广播语义要让每个实例各自接收同一条失效事件，或者每实例使用独立消费组。项目配置 `consumerType: broadcast` 正是为了这个目的。

## Q63 `[P1]` 缓存穿透怎么处理，项目布隆过滤器在哪里有用

**先理解**

穿透是查询的数据本就不存在，因此每层普通缓存都可能 miss 并反复压到数据库。

**面试回答**

> 穿透是查询本来就不存在的数据，缓存和数据库都无法命中。项目有节目详情布隆过滤器配置，可在访问缓存和数据库前判断 programId 是否可能存在；明确不存在就快速返回。还可以缓存短 TTL 空值、校验 ID 格式和限流。
>
> 布隆过滤器有假阳性，没有假阴性：它说不存在时一定不存在，说可能存在仍需继续查询。删除数据和过滤器重建也要设计，不能把布隆判断当成数据库事实。

## Q64 `[P1]` 缓存雪崩怎么处理

**先理解**

雪崩是大量 key 同时失效或整个缓存层不可用，远大于单个热 key 击穿的影响面。

**面试回答**

> 雪崩是大量 Key 同时过期或 Redis 整体不可用，流量集中回源。措施包括过期时间随机化、分批预热、热点逻辑过期、Redis 高可用、限流熔断、隔离线程池和数据库保护。项目很多节目缓存按演出时间过期，若大量节目同一时间点结束会有集中失效风险，因此应增加合理抖动或按业务不再查询后自然淘汰。

## Q65 `[P1]` 座位 Hash 会不会成为 Big Key

**先理解**

Big Key 的问题不只是占内存，还会放大单命令耗时、删除、复制、迁移和主从切换开销。

**面试回答**

> 会。一个热门场馆单票档可能有大量 Seat JSON，脚本还使用 `HVALS` 全量读取和解码。Big Key 会增加网络包、Redis 单命令执行时间、删除阻塞、主从同步和迁移成本。
>
> 项目已经按 programId+ticketCategoryId 拆 Key；进一步可按区域、排或固定桶继续拆分，座位 value 只保留必要字段，异步 `UNLINK` 删除，扫描用 `HSCAN`，自动配座维护更小的候选索引，并监控 key size 和 slowlog。

## Q66 `[P1]` Cache Aside 更新顺序怎么选

**先理解**

Cache Aside 无法用两个独立写操作保证绝对原子，目标是选择差错窗口更小、可修复的顺序。

**面试回答**

> 通用读缓存场景优先“更新数据库成功后删除缓存”，下一次读再回填。先删缓存再更新数据库时，并发读可能在数据库更新前把旧值重新写回缓存；更新数据库再删缓存也有删失败窗口，所以需要重试、消息或 binlog 订阅兜底。
>
> 票务库存不能简单套 Cache Aside，因为它是高频竞争状态。项目把库存状态迁移放进 Lua，再异步更新数据库并用流水对账；节目静态详情和本地缓存失效才更接近 Cache Aside。

# 第八部分：分库分表、分布式 ID 与迁移

## Q67 `[P0]` 为什么订单要分库分表，什么时候才该分

**先理解**

分库分表是单库在容量、写吞吐、索引层级或维护窗口达到瓶颈后的水平扩展，不是默认架构。

**面试回答**

> 订单和购票人明细持续增长，单表索引层级、缓存命中、备份恢复和写热点都会恶化；单库还受连接数、IOPS 和存储上限约束。项目用两库、每库四张订单表分摊数据和写压力，并让同一用户及其订单能定向路由。
>
> 但分片会带来跨分片分页、聚合、事务、唯一约束、扩容和运维成本，数据量和负载在单库可承受时不应为了技术亮点提前分。是否拆分应由容量评估、慢查询和增长趋势决定。

## Q68 `[P0]` ShardingSphere-JDBC 的工作原理是什么

**先理解**

它在应用进程内将对逻辑表的 SQL 解析、路由、改写到多个真实库表，再归并结果。

**面试回答**

> 它作为增强 JDBC 驱动工作在应用进程内，接收逻辑 SQL，解析 SQL 和分片条件，根据规则路由到真实数据源和物理表，改写 SQL，执行后再归并结果。优点是业务仍按逻辑表编程、部署简单；缺点是每个应用实例都承担解析和路由，复杂 SQL、广播查询和跨分片归并可能成本很高。
>
> 项目在订单服务把 datasource driver 指向 ShardingSphereDriver，`d_order` 使用 order_number 和 user_id 的复合自定义分片算法。

## Q69 `[P0]` 什么是项目里的订单号基因法

**先理解**

基因法是把路由所需的用户 bit 保留在订单号中，使两种查询键能计算出同一分片。

**面试回答**

> 订单号生成时把 userId 的低六位嵌入订单号低六位，路由算法无论拿到 userId 还是 orderNumber，都能提取相同基因。分表取低 `log2(tableCount)` 位，分库先右移表基因位，再取 `log2(databaseCount)` 位。
>
> 当前两库四表时，表使用 bit0—1，库使用 bit2，位不重叠，因此八个物理分片都可能被使用。它解决的是用户维度查询和订单号查询定位一致，以及早期算法库表共用低位导致分布浪费的问题。

## Q70 `[P0]` 为什么分库位和分表位不能使用同一段 bit

**先理解**

如果库索引和表索引取自同一段位，两者就会强相关，部分物理库表组合永远不会被路由。

**面试回答**

> 如果库和表都用 `value % N` 或相同低位，库索引和表索引会强相关。例如两库四表时，某些库表组合永远无法出现，实际八个物理分片只用到一部分。项目把分表放低位、分库放跳过表位后的中位，使库表索引独立组合，提升分布均匀性和资源利用率。

## Q71 `[P0]` 为什么用 userId 或 orderNumber 都能查到同一个分片

**先理解**

关键是订单号在生成时保留了 userId 的路由基因，而两种算法取相同位段。

**面试回答**

> `getOrderNumber(userId)` 固定保留 userId 低六位，后续订单号高位由时间、机器和序列组成，但低六位不变。自定义库表算法对两个字段采用同一位提取规则，所以使用 userId 查用户订单，或使用 orderNumber 查订单详情，都会得到相同库表索引。

## Q72 `[P1]` 查询没有分片键会怎样

**先理解**

路由器无法缩小目标分片时，只能向所有候选节点执行并归并，查询成本随分片数放大。

**面试回答**

> 自定义算法在没有 order_number 和 user_id 条件时返回全部真实库表，ShardingSphere 会广播路由并归并结果。数据量大时这会放大连接、扫描、网络和排序成本。因此线上接口应强制携带分片键；管理端跨分片查询可使用离线数仓、ES、汇总表或专门的聚合服务，而不是频繁扫所有订单分片。

## Q73 `[P1]` 分库分表后怎么做全局 Top100 和分页

**先理解**

全局排序需要把每个分片的有序局部结果合并，深分页还会在每个分片重复扫描大量 offset。

**面试回答**

> 小规模可让每个分片按相同排序取本地 Top100，再在应用层做 k 路归并取全局 Top100；不能先把全量数据拉回。深分页会让每个分片扫描大量 offset，推荐游标分页，把上页最后的排序键和唯一 ID 作为 seek 条件。
>
> 高频排行榜或运营查询应在写入时同步到 ES、ClickHouse 或汇总表，用专门的分析存储完成，避免交易库跨分片实时聚合。

## Q74 `[P0]` 分布式 ID 为什么不用数据库自增或 UUID

**先理解**

分布式主键要同时考虑全局唯一、生成吞吐、趋势递增、存储成本和可用性。

**面试回答**

> 数据库自增在多库下难保证全局唯一，并形成中心写瓶颈；UUID 本地生成方便，但长度大、无序，作为 InnoDB 聚簇主键容易增加索引空间和页分裂。雪花类 ID 本地高性能、趋势递增、可编码时间和机器信息，更适合分布式订单。
>
> 项目普通实体 ID 使用百度 UidGenerator，订单号使用自定义 Snowflake 并嵌入 userId 六位基因。代价是依赖时钟和 workerId 唯一性，固定基因位也限制最大库表组合。

## Q75 `[P1]` 雪花算法遇到时钟回拨怎么办

**先理解**

雪花 ID 把时间戳放入 ID，时间向后跳可能重新进入已使用的时间区间，因而威胁唯一性。

**面试回答**

> 当前 `SnowflakeIdGenerator` 检测到时间小于上次时间时，五毫秒以内尝试等待两倍偏移后重试，仍回拨或超过五毫秒就拒绝生成，避免重复 ID。百度 UidGenerator 路径对秒级回拨则直接抛异常。
>
> 生产上还要使用稳定时钟源、禁止运行中大幅回拨、监控 NTP，workerId 通过可靠注册分配。需要更强可用性时可用 Leaf 号段或双 buffer，代价是依赖数据库/服务端。

## Q76 `[P0]` 当前迁移服务如何扩容

**先理解**

扩容迁移要把旧路由下的数据重算新位置，并在可控压力下处理改变位置的记录。

**面试回答**

> `ShardingMigrationService` 遍历旧库旧表，用 HintManager 强制读指定物理表，以自增 ID 游标和 batchSize 分批扫描；再按新库表数量重新计算目标位置，只迁移位置变化的数据；按目标库表分组 Hint 插入，再从源表物理删除。它支持 dry-run 只统计，也每十批短暂停顿控制压力。
>
> 这个实现展示了离线迁移基本思路，但还不是无损在线扩容完整方案：它主要处理主订单表，插入和删除没有形成真正跨库原子事务，也缺少业务双写、迁移进度表、校验、切流和回滚。

## Q77 `[P0]` 如何把迁移改造成生产可用的在线扩容

**先理解**

在线迁移的难点不是复制历史数据，而是全量复制期间仍有增量写入，切换还必须可校验、可回滚。

**面试回答**

> 我会分为准备、全量、增量、校验、切换、清理六步。先创建目标分片和版本化路由；开启旧新双写或用 binlog 捕获增量；按主键游标分批复制主订单及所有关联子表，写入必须幂等；持续校验行数、主键、金额和抽样校验和；增量追平后短暂停写或设置切换水位，原子发布新路由；观察稳定后再延迟清理旧数据。
>
> 每批迁移要有持久化进度和状态，失败可续传；切换前可 dry-run，切换后可快速回滚路由。项目当前 `insertToTarget()` 和 `deleteFromSource()` 的 `@Transactional` 还存在同类内调用无法经过 Spring 代理的问题，而且跨库本就不能靠普通本地事务解决，这正是需要状态机和幂等迁移的原因。

## Q78 `[P1]` 项目所说的虚拟分片路由是否已经完整落地

**先理解**

虚拟分片只有在真实路由链路查询映射、支持版本切换时才算落地，仅有映射表不够。

**面试回答**

> 当前仓库 SQL 已创建 1024 个逻辑分片到物理库表的 `d_sharding_route_mapping`，订单服务也有对应实体，但我没有在实际 ShardingSphere 订单路由算法中找到查询或缓存这张映射表的逻辑。现行 `DatabaseOrderComplexGeneArithmetic` 和 `TableOrderComplexGeneArithmetic` 仍直接按固定基因位计算物理索引。
>
> 因此准确说法是“仓库有虚拟分片的数据模型和初始化数据，当前主路由仍是方案一固定基因法；虚拟映射接入还需实现”。如果接入，路由应从订单号计算 logicalShardId，再通过本地缓存映射到物理分片，并用版本号原子刷新映射，避免扩容切换期间不同实例路由不一致。

# 第九部分：Gateway、鉴权与微服务治理

## Q79 `[P0]` 一个请求经过 Gateway 时做了哪些事

**先理解**

网关不是单纯转发器，它把跨服务的通用能力放到业务服务之前。

**面试回答**

> `RequestValidationFilter` 先生成或沿用 traceId，并携带灰度标记；对 JSON 请求读取并重建 body。需验证的接口根据渠道 code 取密钥，可选解密 `businessBody`，再验 RSA 签名；受保护路径校验 JWT，解析 userId。之后用 Redis Lua 执行 IP、用户和 URL 组合维度的接口频控，最后把 traceId、灰度标记、code 和 userId 写入下游请求头。
>
> 要区分安全、鉴权和流量治理：RSA 签名防参数被篡改，加密保护明文，JWT 识别用户，限流保护系统容量。它们不能相互替代。

## Q80 `[P1]` RSA 验签、RSA 加密和 JWT 有什么区别

**先理解**

三者分别解决完整性/来源、机密性和身份声明问题，“有签名”不等于“内容已加密”。

**面试回答**

> 验签是让发送方对规则化参数摘要签名，服务端用公钥校验，主要保证完整性和来源；加密是用公钥加密、私钥解密，主要保护机密性；JWT 是携带身份 claim 和过期时间的 token，签名可防篡改，但 payload 通常只是 Base64URL 编码，不是加密。
>
> 项目根据渠道数据取签名公钥、数据私钥和 token secret。生产上还应防重放：把 timestamp、nonce 纳入签名，校验时间窗并记录 nonce；同时做密钥轮换和版本化。

## Q81 `[P1]` WebFlux 中为什么请求体读完还要重新包装

**先理解**

Reactive 请求体是一次性数据流，上游过滤器消费后，必须缓存并重建才能让下游再读。

**面试回答**

> WebFlux 的 body 是基于 `Flux<DataBuffer>` 的一次性流，网关为了解密、验签先消费了它，如果直接往下传，下游将读不到 body。项目用 `CachedBodyOutputMessage` 写入处理后的 body，再通过 `ServerHttpRequestDecorator` 重写 `getBody()` 和 headers。
>
> 这里要注意大 body 的内存占用、DataBuffer 泄漏、Content-Length 和 Transfer-Encoding，也不能在 Netty 事件线程里执行阻塞 IO。

## Q82 `[P0]` 项目的 Redis Lua 限流是怎么做的

**先理解**

限流的核心是在一个时间窗内统计请求，超过容量时拒绝或降级。

**面试回答**

> 网关先用 IP、可选 userId 和 URL 生成隔离 key。普通规则在 Lua 中 `INCRBY` 计数，首次写入时设统计窗口 TTL；达到阈值后写限制 key 并设生效时间。深度规则用 ZSet 记录触发点，在配置的时段和滑动窗口内统计。Lua 使计数、设过期和触发判定不被并发请求插入。
>
> 当前脚本把 JSON 参数放在 `KEYS[1]` 而不是 `ARGV`，语义不规范；Redis Cluster 下实际读写多个 key 还要保证同 slot。生产上要配合全局容量、热 key 散列和降级策略。

## Q83 `[P1]` Redis 限流失败时是 fail-open 还是 fail-close

**先理解**

限流组件本身也会故障，此时要在业务可用性和下游容量安全之间显式选择。

**面试回答**

> 这是业务取舍。fail-open 是限流组件故障时放行，保可用性但可能击穿下游；fail-close 是直接拒绝，保护容量但会把 Redis 故障放大为全站不可用。应根据接口等级选择：登录和查询可谨慎放行，下单类应用本地容量限制保底。
>
> 当前 `ApiRestrictService` 捕获 Redis/Lua 异常后只记日志，`triggerResult` 保持 0，实际是 fail-open。改进可以在网关使用本地令牌桶/并发信号量保底，并对 Redis 异常率告警，而不是无声放行。

## Q84 `[P0]` 项目中本地 Semaphore 限流有什么问题

**先理解**

Semaphore 控制同时持有许可的并发数，不自动表示 QPS；获取和释放还必须严格成对。

**面试回答**

> 它更准确是单实例并发数隔离，不是“每秒 N 个”的速率限制；多个 Gateway 实例各有一份许可，全局上限会随实例数增长。更重要的是，`RequestValidationFilter` 无论 `tryAcquire` 是否成功都在 `finally` 里 `release`；超时失败后也会增加许可，长期可导致上限失效。
>
> 修复时用 `boolean acquired` 记录获取结果，只在成功时释放；若需 QPS 限流，应用令牌桶或滑动窗口。还要注意 WebFlux 事件线程不应阻塞等待一秒，更适合立即失败或非阻塞实现。

## Q85 `[P1]` Sentinel 和项目自定义限流有什么区别

**先理解**

通用容量治理和带用户/IP/时段的业务防刷规则属于不同层，可以组合而不必互斥。

**面试回答**

> Sentinel 更适合按路由、API 组做 QPS、并发线程、熔断降级和热点参数治理，有统计滑窗口和规则控制面；项目自定义 Lua 更偏业务规则，能组合 IP、用户、URL 和特定时段，但维护成本和 Redis 依赖更高。
>
> 两者可分层：Sentinel 保护系统容量，业务 Lua 防刷和做精细规则。但仓库里 `GatewaySentinelConfiguration` 未见 `@Configuration` 或显式导入，Nacos 规则数据源也被注释，面试时应说“有依赖和候选配置，尚需验证注入和持久化”。

## Q86 `[P1]` Nacos、OpenFeign 和 LoadBalancer 在调用中各做什么

**先理解**

三者分别解决“有哪些实例”、“怎么声明调用”和“这次选哪个实例”。

**面试回答**

> 服务实例向 Nacos 注册并获取服务列表；OpenFeign 把 Java 接口转成 HTTP 请求；Spring Cloud LoadBalancer 从实例列表选择目标。项目还用 Nacos 实例 metadata 中的 gray 标记做灰度筛选，并通过请求头传播灰度上下文。
>
> Feign fallback 只是降级出口，不等于可以吞掉错误。例如库存扣减失败必须阻断下单并补偿，不能返回伪成功。

## Q87 `[P1]` traceId 和业务上下文怎么跨线程传递

**先理解**

ThreadLocal/MDC 只属于当前线程，线程池任务会换到另一条可复用线程，所以必须显式复制和清理。

**面试回答**

> 网关生成 traceId 并写入请求头，服务端过滤器放入 MDC 和 `BaseParameterHolder`，使日志和 Feign 调用可继续携带。线程池切换后 ThreadLocal 不会自动继承，所以 `BusinessThreadPool` 提交时快照父线程 MDC 和业务参数，任务前设置，`finally` 恢复工作线程原现场。
>
> 不能只设置不清理，否则线程复用会串用户和 traceId。对 Kafka 异步链路则应把 traceId 写入消息 header 或 payload，消费时重建上下文。

# 第十部分：线程池、监控、压测与故障定位

## Q88 `[P0]` 项目线程池参数是什么，合理吗

**先理解**

线程池参数不能仅靠公式，要由任务的 CPU/等待比、下游容量和延迟目标决定。

**面试回答**

> `BusinessThreadPool` 的 core 是 CPU+1，max 按 CPU/0.2 计算，约为 5N，有界 `ArrayBlockingQueue` 是 600，keepAlive 60 秒，拒绝策略是 AbortPolicy。这相当于假设任务有较多 IO 等待，但当前没有代码中的测量证据说明 0.2 为何适合。
>
> 我会先区分 CPU 密集和 IO 密集任务，压测得到平均计算时间与等待时间，用 `Ncpu*(1+W/C)` 得到起点，再受数据库连接数、Redis/HTTP 下游并发上限约束。最终以活跃线程、队列长度、拒绝数、P99 和下游错误率调参。

## Q89 `[P1]` 为什么要有界队列，队列越大越好吗

**先理解**

队列是用空间吸收短时流量波动，不能提高长期处理能力；过大只会隐藏过载并拉高延迟。

**面试回答**

> 无界队列会在输入长期大于处理能力时无限堆积，最后延迟失控或 OOM。有界队列把系统容量显式化，满了后通过拒绝、限流或降级形成背压。
>
> 队列越大只是容纳更多已过时任务。应根据可接受的排队时间估算，并监控 queue utilization 和 oldest-task-age；下单等强时效任务宁可快速失败重试，也不要在队列里等到业务失效。

## Q90 `[P0]` AbortPolicy 会不会丢任务

**先理解**

拒绝策略只决定线程池不接任务时如何通知调用方，业务是否丢失要看上层补偿。

**面试回答**

> AbortPolicy 会抛 `RejectedExecutionException`，任务不会进入线程池。是否丟失取决于上层是否捕获并持久化重试；只打日志或没有处理就是业务丢失。CallerRuns 可以用调用者线程形成背压，但在 Kafka 消费线程或 WebFlux 事件线程上可能阻塞关键线程，也不能乱换。
>
> 项目延迟队列消费者先从队列取出消息再提交执行器，若此时被 AbortPolicy 拒绝，存在消息已移除但业务未执行的窗口。需要捕获拒绝后重新入队/持久化，或用存储系统先记录执行权并由对账补偿。

## Q91 `[P0]` 这个项目应监控哪些核心指标

**先理解**

监控要把用户体感、资源饱和度、中间件健康和业务正确性联系起来，只看 CPU 找不到大部分分布式故障。

**面试回答**

> 我会按四层看。入口层看 QPS、限流数、错误率和 P50/P95/P99；资源层看 CPU、GC 暂停、堆、线程池活跃数/队列/拒绝、DB 和 Redis 连接池；中间件层看 Redis 命中率、热 key、慢查询，Kafka 生产失败、consumer lag、重试和死信；业务层看 Lua 扣库成功率、异步建单时延、异常订单数、未支付超时、库存对账差异和退款异常。
>
> 仓库引入 Actuator、Prometheus 导出和 SkyWalking 工具包，但“有依赖”不等于“仪表盘和告警已验收”。面试中应给出告警门槛、链路定位方法和库存差异处置 SOP。

## Q92 `[P0]` 如何做一次可信的抢票压测

**先理解**

压测不是只报一个 QPS，必须有环境、数据、口径和正确性验证。

**面试回答**

> 我会固定机器配置、服务实例数、JVM、Redis/Kafka/MySQL 拓扑和网络，预热 JIT 和缓存，为每个虚拟用户生成独立 token、购票人和幂等请求，避免所有流量被防重拦下。分别做单接口容量、突发峰值、稳态、耐久和故障注入。
>
> 结果同时报告吞吐、P95/P99、成功率和资源拐点，并做业务不变式校验：库存不为负、同座位不重复、同用户不超限、Redis 与 DB 最终一致、消息积压可恢复。仓库自带报告只能称为“项目方报告”，未亲测不能说成自己的结果。

## Q93 `[P1]` 线上 P99 突然升高，你怎么排查

**先理解**

P99 描述尾延迟，容易被排队、GC、热点、下游长尾和超时重试放大，需要沿链路找首个拐点。

**面试回答**

> 先确认影响面和变更时间，用 traceId 将慢请求分解到 Gateway、Lua、Feign、Kafka 回调等待和 DB；然后对照 CPU、GC、线程池队列、连接池、Redis 慢命令/热 key、Kafka lag 与 MySQL 慢 SQL，找出第一个开始恶化的环节。
>
> 这个项目我会特别检查自动选座的 `HVALS + sort`、Kafka 生产回调 `await()` 无超时、线程池队列以及分片键缺失导致的广播路由。处置时先限流/降级和回滚变更，再基于证据修复，不在线上盲目调大线程和队列。

## Q94 `[P1]` 流量增长十倍，系统最可能先卡在哪里

**先理解**

系统容量由最窄环节决定，而最窄环节会随请求结构、数据热点和下游状态变化。

**面试回答**

> 不能凭组件名猜，要通过分层压测找容量曲线。从源码风险看，热门节目的 Redis 单 key 和自动选座全量遍历是首要热点；随后是 Kafka 分区和订单消费吞吐、MySQL 连接池、订单写入以及线程池排队。网关单机限流与 Redis 频控也可能反而成为瓶颈。
>
> 扩容前先用预售排队和用户/节目级限流削峰，再将库存单 key 设计、选座索引、Kafka 分区数与 consumer 并行度、分片库容量一起计算，并保留回滚和故障降级通道。

## Q95 `[P2]` 如何设计这个项目的故障演练

**先理解**

故障演练不是随机杀进程，而是带着正确性假设、爆炸半径和恢复目标验证容错闭环。

**面试回答**

> 我会围绕不变式演练：在 Lua 成功后分别中断 Kafka、消费者和 MySQL；制造重复消息和长时间 backlog；让支付回调与超时关单并发；重启 Redis 验证持久化窗口；打满线程池和连接池。每个场景都验证无负库存、无重座、状态单向迁移、差异可被发现并恢复。
>
> 演练前定义爆炸半径、停止条件和回滚，先在隔离环境进行；记录检测时间、恢复时间、补偿成功率和人工步骤，演练后把缺口变成告警、自动补偿或运行手册。

# 第十一部分：Spring、事务、设计模式与 Java 17

## Q96 `[P0]` 项目中用了哪些设计模式，不要只报名字

**先理解**

设计模式要回答“哪个变化点被隔离”，而不是根据类名猜模式。

**面试回答**

> 下单入口用策略模式：V1—V4 实现统一下单接口，Context 根据版本选择，使演进算法与 Controller 解耦。下单前校验用组合/责任链思路：各 handler 校验用户、票档、限购等，便于排序和增减。延迟队列根据业务类型找对应 consumer，属于工厂+策略。
>
> `@RepeatExecuteLimit` 和分布式锁封装体现了模板/AOP：切面统一提取 SpEL key、加锁、执行和释放，业务方法只声明规则。模式的价值是隔离变化；如果只为了背概念而增加类层级，反而会过度设计。

## Q97 `[P0]` `@Transactional` 为什么在同类调用中可能失效

**先理解**

Spring 声明式事务默认由代理拦截方法调用，不是看到注解就自动改写方法体。

**面试回答**

> 外部调用经过 Spring AOP 代理，代理才会开启、提交或回滚事务；同一对象内用 `this.method()` 调用时直接进入目标对象，绕过代理，被调方法上的事务配置可能不生效。
>
> 迁移服务中批处理方法内调用带注解的 `insertToTarget()` 和 `deleteFromSource()` 就有这个风险。可把事务边界抽到另一个 Bean，或用 `TransactionTemplate`；但即使代理生效，普通本地事务也不能原子覆盖新旧两个分片。

## Q98 `[P0]` 订单服务一个本地事务能包住 Feign 调用吗

**先理解**

本地事务的原子边界是当前数据源连接，HTTP 另一端的提交不会随本地 rollback 自动撤销。

**面试回答**

> 不能。本地事务只能控制当前数据源连接上的 DB 操作，Feign 调用的节目服务有自己的进程和事务。即使订单方法标了 `@Transactional`，也可能出现节目 DB 已扣库存、订单 DB 写入失败的中间状态。
>
> 解决思路是 Saga/TCC、可靠消息或本地消息表，关键是每步幂等、有状态机、可补偿并能对账。项目现有异常订单集合和库存流水是补偿基础，但不应宣称一个 Spring 本地事务已保证跨服务原子性。

## Q99 `[P1]` 为什么不能遇到一致性问题就用 Seata

**先理解**

分布式事务方案各自用延迟、吞吐、业务侵入和可用性换取一致性，没有零成本通用解。

**面试回答**

> Seata AT 对数据库本地事务做代理和回滚日志，提供编程便利，但热点抢票链路会引入全局锁竞争、协调器依赖和更高延迟；它也不能自然把 Redis Lua、Kafka 和第三方支付纳入同一 ACID 事务。
>
> 核心抢票更适合短事务+异步事件+幂等补偿+对账。对低并发、参与者都是可控数据库、确实需要强一致的后台流程，再评估 Seata。项目中有相关依赖/早期代码不等于 V4 主链路已由 Seata 保障。

## Q100 `[P1]` Spring 默认事务在什么异常下回滚

**先理解**

回滚要同时满足调用经过事务代理、异常离开代理方法且类型命中回滚规则。

**面试回答**

> 默认对 `RuntimeException` 和 `Error` 回滚，对 checked exception 不自动回滚；项目多处使用 `rollbackFor = Exception.class` 扩大到所有 Exception。但如果异常在方法内被 catch 后吞掉，代理看不到异常，仍可能提交。
>
> 还要注意代理边界、方法可见性、事务传播、多数据源和长事务。外部 HTTP/Kafka/Redis 操作不会随 MySQL 回滚，需要单独的一致性设计。

## Q101 `[P1]` 项目用 Java 17，面试时怎么讲

**先理解**

要区分“项目的运行基线是 Java 17”和“项目真正使用了哪些 17 时代特性”，不能把版本号当经验。

**面试回答**

> 仓库父 POM 指定 Java 17，Spring Boot 3.3.0 也使用 Jakarta 命名空间。我会讲两类价值：语言层有 record、sealed class、模式匹配和 text block，能减少 DTO 样板代码并更清晰表达有限状态；JVM 层 Java 17 是 LTS，有持续的 G1 改进，也可按延迟和堆规模评估 ZGC。
>
> 但项目“运行在 17”不等于已大量使用新语法，也不要把 Java 21 才正式的虚拟线程说成 Java 17 特性。线上还应通过 GC 日志和 JFR 验证收集器与参数，不是只背默认值。

## Q102 `[P0]` 请说三个项目现有缺陷，你会先改哪个

**先理解**

好的回答不是贬低项目，而是用影响面、发生概率和修复成本做优先级。

**面试回答**

> 第一优先级是建单事件可靠性：当前生产回调等待无超时、retries 只有 1，消费端自动提交且捕获异常。它直接影响“扣了库存却没有订单”，所以我会先引入可靠事件记录/Outbox、`acks=all`、有界重试、手动提交和死信队列，并让库存对账调度真正运行。
>
> 第二是延迟消费执行器拒绝可能造成关单丢失，要捕获并持久化重试；第三是网关 Semaphore 在未获得许可时也 release，会使容量限制逐渐失效。其他中长期改进包括 Redis Cluster 同槽改造、虚拟分片路由接入和无损迁移闭环。

## Q103 `[P0]` 你如何证明自己真的掌握了这个项目

**先理解**

“掌握”的证据是能预测中间状态、指向源码并用实验验证，不是能复述项目介绍。

**面试回答**

> 我不只能画正常链路，还能从任意一个中间状态往下追。例如 Lua 成功后 Kafka 失败时库存如何回补；消息重复时注解、查询和唯一索引如何分层幂等；支付和取消竞争时为什么要用同一订单号锁；以及对账如何区分 Redis 流水和 DB 流水。
>
> 我也能指出对应源码、当前边界和可验证的改进，而不把“方案应该有”说成“仓库已实现”。最有力的证据是一组可复现的压测和故障注入记录，加上修复前后指标对比。

## Q104 `[P0]` 如果只有 90 秒，怎么回答“项目亮点和不足”

**先理解**

90 秒回答要建立一条主线：业务难题、三个关键机制、一个真实边界和优先改进，而不是技术栈罗列。

**面试回答**

> 项目的主线是高并发票务库存和异步订单。第一个亮点是用 Redis Lua 把余票检查、选座、扣库存、座位迁移和流水写入变成一个原子操作；第二个是 Kafka 异步建单削峰，通过订单号幂等和唯一索引防重；第三个是支付、超时取消用同一订单锁串行状态变化，并以延迟消息记录和库存流水对账处理异常。
>
> 我不回避它的边界：建单 Kafka 当前自动提交 offset，生产可靠参数和对账闭环不完整；Redis 还是单机配置，虚拟分片路由尚未接入。我会优先把建单改为可靠事件+手动提交+死信与对账，然后用故障注入证明中间件异常后仍无负库存、无重复订单，且差异可恢复。
