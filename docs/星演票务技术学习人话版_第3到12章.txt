星演票务项目技术学习人话版（第 3～12 章）


第 3 章：Gateway、令牌桶、WebFlux、event-loop 和并发舱壁

一、一次请求进来以后，按什么顺序走

用户请求下单
→ Gateway 先接到请求
→ 清除客户端自己填写的 userId、code、programId 等不可信请求头
→ 从已经验证的 JWT 和请求体重新得到真实用户、真实节目
→ 做用户限流
→ 做节目限流
→ 做全局限流
→ 检查当前正在处理的请求是否太多
→ 没超才转发给下游服务
→ 下游处理结束，不管成功、失败还是连接中断，都归还并发许可

你之前问“检查当前正在处理的请求是不是太多是哪一步”，答案就是：

Redis 令牌桶限流全部通过之后，ConcurrencyBulkheadFilter 调用 Semaphore.tryAcquire() 的这一步。

tryAcquire() 成功：说明还有空位，请求继续。
tryAcquire() 失败：说明当前在途请求已经达到上限，立即拒绝，不在网关里继续排队。


二、Gateway 是什么

Gateway 就像整个系统的大门和安检口。

前端本来可以直接找订单服务、节目服务、用户服务，但项目让请求先经过 Gateway。Gateway 可以统一做：

身份检查
清理伪造参数
限流
并发保护
路由到真正的服务

它通常不负责创建订单、扣库存这些业务，只负责决定“这个请求能不能进去、应该交给谁”。


三、WebFlux 是什么

WebFlux 是 Spring 的一种网络请求处理方式。它适合用少量线程同时照看很多连接。

普通阻塞写法像这样：

线程发出 Redis 请求
→ 原地等 Redis 返回
→ 等待期间这个线程什么也做不了

WebFlux 的非阻塞思路像这样：

线程发出网络请求
→ 登记“结果回来后继续做什么”
→ 线程先去处理别的连接
→ Redis 结果回来后再继续后面的步骤

它不是让 Redis 突然变快，而是让线程不要在等待网络时一直被占住。


四、event-loop 是什么

event-loop 可以理解成几个很忙的调度员。

每个调度员同时照看很多连接：

连接 A 的数据到了，处理一下 A
连接 B 的数据到了，处理一下 B
连接 C 还在等网络，先不管 C

因为调度员数量不多，所以调度员不能被一个慢操作卡住。

如果直接在 event-loop 上运行阻塞 Redis：

Redis 卡 2 秒
→ 当前 event-loop 线程也卡 2 秒
→ 归这个线程照看的其他连接都不能及时处理
→ 一个 Redis 慢请求拖慢一批用户

所以代码把阻塞 Redis 调用切到 boundedElastic。

boundedElastic 可以理解成专门处理阻塞工作的备用工人池。event-loop 把阻塞工作交出去，自己继续照看连接。但是备用工人也不是无限的，所以外面还要用并发舱壁控制数量。


五、限流和限并发为什么不是一回事

限流管“单位时间来了多少请求”。
并发舱壁管“现在有多少请求还没处理完”。

例子：

平时每秒 100 个请求，每个请求 50 毫秒完成，在途请求不多。

下游突然变慢，每个请求要 2 秒：

第 1 秒进来 100 个，还没做完
第 2 秒又进来 100 个
第 3 秒继续进来
→ 请求越积越多

这时候 QPS 可能仍然没有超过每秒 100，但正在处理的请求已经很多。因此限流不能代替限并发。


六、为什么叫舱壁

轮船会被隔成多个舱。一个舱进水，不应该把整条船都淹掉。

系统里的舱壁也是限制故障范围：

最多允许 N 个请求进入下游
→ 下游变慢时，最多拖住 N 个请求
→ 后面的请求快速失败
→ 不让线程、连接池和内存被无限占满

Semaphore 就像一盒数量固定的入场券。

请求进入：拿一张券。
请求结束：还一张券。
没有券：说明当前请求太多，立即拒绝。


七、令牌桶按什么流程工作

令牌桶里保存两样东西：

现在还剩多少 token
上次补 token 是什么时候

每次请求到来：

读取当前时间
→ 根据距离上次补充经过了多久，计算应补多少 token
→ 补完不能超过桶容量
→ token 至少有 1 个，就扣 1 并放行
→ token 不足，就拒绝

容量决定能承受多大的短时突发。
补充速度决定长期平均每秒允许多少请求。

例如容量 10、每秒补 2 个：

安静一段时间后桶里有 10 个
→ 突然来的前 10 个请求可以快速通过
→ 之后长期只能按每秒约 2 个的速度通过

计算和扣减放在同一个 Redis Lua 里，是为了防止两个 Gateway 同时看到“最后一个 token”，然后都放行。


八、USER、PROGRAM、GLOBAL 三层分别保护谁

USER：防止一个账号疯狂刷请求。
PROGRAM：防止某一场热门节目冲垮库存服务。
GLOBAL：防止所有流量加起来超过整个系统容量。

执行顺序是：

USER 通过
→ PROGRAM 通过
→ GLOBAL 通过
→ 本机并发舱壁通过
→ 才进入下游


九、429 和 503 分别是什么意思

429：限流系统正常，只是配额已经用完。意思是“请求太多”。

503：Redis 限流依赖异常，当前无法安全判断是否应该放行。意思是“保护系统本身出问题”。

下单是高风险写操作，Redis 限流坏了以后选择 fail-closed：

无法确认是否超限
→ 返回 503
→ 不让请求无保护地冲击库存

普通详情查询可以根据业务风险考虑 fail-open 或本地降级，但不能所有接口共用一个策略。


第 4 章：Redis 数据结构、Cluster 和 Lua 原子预占

一、自动选座从哪里开始

用户说“我要 3 张连座票”以后：

Java 先从 Redis 的 available ZSET 读取一小批可售座位
→ 根据稳定 requestId 算一个稳定起点
→ 每页最多看 64 个座位
→ 最多整理出 32 组候选连座
→ 每组最多 6 张票
→ 把第一组候选交给 Lua 做最终裁决
→ Lua 说座位已经被抢，就换下一组重试

Java 只是推荐候选，不决定座位最终归谁。

因为 Java 读完以后到 Lua 执行以前，其他用户可能已经抢走座位。真正决定归属的是 Lua 中再次检查并写入的步骤。


二、为什么不让 Lua 在全场座位里搜索

Redis 执行 Lua 时，其他命令不能插进脚本中间。

如果 Lua 里面做这些重活：

读取全场所有座位
JSON 解码
排序
搜索连座

座位越多，脚本运行越久，其他请求等待越久。

所以工作拆开：

Java 做耗时但不决定正确性的候选搜索。
Lua 只检查最终几张座位并完成权威写入。


三、预占涉及的 Redis 数据

ready：这个节目库存是否准备好。
maintenance：库存是否正在维护或重建。
meta Hash：每个座位的官方票档、价格等资料。
available ZSET：当前可售座位。
owner Hash：每个已经预占的座位属于哪个 intentId。
reservation Hash：一次预占的完整信息。
result Hash：预占成功后返回的座位快照。
receipt String：短期幂等回执。
accountCount Hash：账号已经买了多少张。
expiration ZSET：reservation 什么时候到期。
event Stream：预占成功后等待发送到 Kafka 的创建订单事件。
final Hash：reservation 是否已经最终确认或释放。

intentId 可以理解成“一次下单意图的稳定身份证”。同一次请求重试仍使用同一个 intentId。


四、Lua 的完整执行链

1. 先看幂等回执是否已经存在。

存在而且 fingerprint 相同：这是同一次请求重试，直接返回上次结果。
存在但 fingerprint 不同：有人拿同一个幂等身份换了请求内容，拒绝。

2. 再看 result Hash 中是否已经有这个 intentId。

有：说明以前已经预占成功，校验 fingerprint 后返回原座位，不重复扣座。

3. 检查 reservation 是否已经进入最终状态。

已经 SOLD 或 RELEASED，就不能重新预占。

4. 检查库存是否 ready，是否处于 maintenance。

库存没准备好或正在重建，立即拒绝。

5. 检查账号限购。

已购数量 + 本次数量 > 上限，就拒绝。

6. 为每个票档找到对应的 available ZSET。

7. 第一遍只校验所有座位，不写任何数据。

检查同一请求是否重复提交同一个 seatId。
检查座位是否已属于别的 intentId。
检查座位是否还在 available ZSET。
检查座位 meta 是否存在。
检查票档和服务端价格是否仍然一致。

任何一个座位失败，脚本在写入前直接返回。

8. 全部校验成功后，第二遍统一写入。

从 available ZSET 删除座位。
在 owner Hash 写 seatId → intentId。

9. 在同一个 Lua 里 XADD 创建订单事件。

10. 写 reservation、result、receipt、账号计数和到期时间。

11. 返回成功座位快照。


五、为什么必须先检查全部座位再写

Redis Lua 的原子性只表示别的命令不能插进来，不表示脚本发生业务错误时会自动回滚前面的写操作。

错误顺序：

锁座位 1
→ 锁座位 2
→ 检查座位 3，发现不可售
→ 返回失败

这样可能留下前两张已经锁住的半份订单。

正确顺序：

检查座位 1
→ 检查座位 2
→ 检查座位 3
→ 全部通过
→ 一次性写座位 1、2、3


六、为什么 XADD 必须放在锁座 Lua 里

如果流程是：

Lua 锁座成功
→ 返回 Java
→ Java 再发送创建订单事件

可能发生：

座位刚锁成功
→ Java 进程被 kill -9
→ 创建订单事件没有发出
→ 座位锁了，但订单永远不创建

现在改成：

同一个 Lua 锁座
+
同一个 Lua XADD 到 Redis Stream

脚本成功就同时留下事件；脚本失败就两者都不发生。

这只保证 Redis 内部两件事一起发生，不代表 Redis 和 Kafka 是一个跨系统事务。Redis 自己仍受 AOF 和异步复制能力限制。


七、Redis Cluster Hash Tag 是干什么的

Redis Cluster 把 key 分到 16384 个槽。多 key Lua 要求参与脚本的 key 在同一个槽，否则 Redis 不让执行。

项目 key 中都带类似：

{sale:11}

Redis 只用花括号里的内容计算槽。所以同一节目预占需要的 owner、meta、reservation、available、Stream 等 key 都进入同一槽。

programId % 16 把不同节目大致分到 16 个 sale shard。

但一个特别热门的节目仍只有一个槽做最终裁决。要继续扩展，需要按场次或区域拆裁决范围，但一个座位必须始终只有一个权威写者。


八、为什么 seatId 要作为字符串

Java long 可以精确保存很大的整数。
Lua cjson 的 number 使用双精度浮点数，超过 2^53 后可能发生四舍五入。

例如两个不同座位号经过 cjson 后可能变成同一个近似数字。

所以 seatId、ticketCategoryId、ticketUserId 按字符串传给 Lua，并按字符串作为 Hash/ZSET member，避免精度损失。


九、referenceReserveSeats.lua 完整代码

-- KEYS[1]=ready, 2=maintenance, 3=meta, 4=owner, 5=reservation, 6=result,
-- 7=accountCount, 8=eventStream, 9=final, 10=expiration, 11=idempotency receipt,
-- 12..n=available ZSETs.
-- ARGV[1]=intentId, 2=seatsJson, 3=eventPayload, 4=userId, 5=accountLimit,
-- 6=requestFingerprint, 7=expireAtMillis, 8=receiptTtlMillis.
local intent_id = ARGV[1]
local requested = cjson.decode(ARGV[2])
local event_payload = ARGV[3]
local user_id = ARGV[4]
local account_limit = tonumber(ARGV[5]) or 0
local request_fingerprint = ARGV[6]
local empty_seats = cjson.decode('[]')

local raw_receipt = redis.call('GET', KEYS[11])
if raw_receipt then
    local receipt = cjson.decode(raw_receipt)
    if receipt.requestFingerprint ~= request_fingerprint then
        return cjson.encode({success=false, replayed=true, code='IDEMPOTENCY_CONFLICT', seats=empty_seats})
    end
    local replay_result = redis.call('HGET', KEYS[6], intent_id)
    local replay_seats = replay_result and cjson.decode(replay_result) or empty_seats
    return cjson.encode({success=true, replayed=true, code='OK', seats=replay_seats})
end

local previous = redis.call('HGET', KEYS[6], intent_id)
if previous then
    local previous_reservation = redis.call('HGET', KEYS[5], intent_id)
    if not previous_reservation or cjson.decode(previous_reservation).requestFingerprint ~= request_fingerprint then
        return cjson.encode({success=false, replayed=true, code='IDEMPOTENCY_CONFLICT', seats=empty_seats})
    end
    return cjson.encode({success=true, replayed=true, code='OK', seats=cjson.decode(previous)})
end

local final_state = redis.call('HGET', KEYS[9], intent_id)
if final_state then
    return cjson.encode({success=false, replayed=true, code='RESERVATION_' .. final_state, seats=empty_seats})
end

if redis.call('EXISTS', KEYS[1]) == 0 or redis.call('EXISTS', KEYS[2]) == 1 then
    return cjson.encode({success=false, replayed=false, code='INVENTORY_NOT_READY', seats=empty_seats})
end

local purchased = tonumber(redis.call('HGET', KEYS[7], user_id) or '0')
if account_limit > 0 and purchased + #requested > account_limit then
    return cjson.encode({success=false, replayed=false, code='ACCOUNT_LIMIT_EXCEEDED', seats=empty_seats})
end

local available_by_category = {}
for key_index = 12, #KEYS do
    local category = string.match(KEYS[key_index], 'available:(.+)$')
    available_by_category[category] = KEYS[key_index]
end

local seen = {}
local snapshots = {}
for _, selected in ipairs(requested) do
    local seat_id = tostring(selected.seatId)
    local category = tostring(selected.ticketCategoryId)
    if seen[seat_id] then
        return cjson.encode({success=false, replayed=false, code='DUPLICATE_SEAT', seats=empty_seats})
    end
    seen[seat_id] = true

    local available_key = available_by_category[category]
    local owner = redis.call('HGET', KEYS[4], seat_id)
    if owner and owner ~= intent_id then
        return cjson.encode({success=false, replayed=false, code='SEAT_OWNED', seats=empty_seats})
    end
    if not available_key or not redis.call('ZSCORE', available_key, seat_id) then
        return cjson.encode({success=false, replayed=false, code='SEAT_UNAVAILABLE', seats=empty_seats})
    end
    local raw_meta = redis.call('HGET', KEYS[3], seat_id)
    if not raw_meta then
        return cjson.encode({success=false, replayed=false, code='SEAT_META_MISSING', seats=empty_seats})
    end
    local snapshot = cjson.decode(raw_meta)
    if tostring(snapshot.ticketCategoryId) ~= category or tonumber(snapshot.priceInCents) ~= tonumber(selected.priceInCents) then
        return cjson.encode({success=false, replayed=false, code='SEAT_PRICE_OR_CATEGORY_CHANGED', seats=empty_seats})
    end
    snapshot.ticketUserId = selected.ticketUserId
    table.insert(snapshots, snapshot)
end

for _, selected in ipairs(requested) do
    local seat_id = tostring(selected.seatId)
    local available_key = available_by_category[tostring(selected.ticketCategoryId)]
    redis.call('ZREM', available_key, seat_id)
    redis.call('HSET', KEYS[4], seat_id, intent_id)
end
-- XADD 和锁座变更位于同一 Lua 原子操作：进程在脚本返回前被 kill，也不会只锁座不留事件。
local stream_id = redis.call('XADD', KEYS[8], '*', 'intentId', intent_id, 'payload', event_payload)
local reservation = {userId=user_id, ticketCount=#requested, seats=requested,
                     requestFingerprint=request_fingerprint, eventPayload=event_payload, streamId=stream_id}
redis.call('HSET', KEYS[5], intent_id, cjson.encode(reservation))
redis.call('HSET', KEYS[6], intent_id, cjson.encode(snapshots))
redis.call('SET', KEYS[11], cjson.encode({requestFingerprint=request_fingerprint,
                                         eventPayload=event_payload}),
           'PX', tonumber(ARGV[8]))
redis.call('HINCRBY', KEYS[7], user_id, #requested)
redis.call('ZADD', KEYS[10], tonumber(ARGV[7]), intent_id)
return cjson.encode({success=true, replayed=false, code='OK', seats=snapshots})


第 5 章：Redis Stream 到 Kafka 的至少一次链路

一、这一章从哪里开始

第 4 章的 Lua 预占成功时，已经 XADD 了一条“创建订单事件”到 Redis Stream。

现在下一步是：

Redis Stream 中的事件
→ 中继 worker 读取
→ 发送给 Kafka
→ Kafka 消费者创建订单


二、为什么不用 Redis Pub/Sub

Pub/Sub 像现场广播：

消费者在线时能听到。
消费者断线时广播照常过去。
消费者回来以后听不到断线期间的旧消息。

Stream 像有记录的待办箱：

消息可以积压。
消费者读过但没确认的消息会留在 PEL。
消费者崩溃后，其他消费者能重新认领。

PEL 就是 Pending Entries List，中文可以理解成“已经交给消费者，但还没确认完成的消息清单”。


三、实时发送的完整链路

项目有 16 个 sale shard，每个 shard 启一个 worker。

worker 执行 XREADGROUP 阻塞等待新消息
→ Stream 有消息时把消息交给 consumer group
→ 消息进入 PEL
→ publisher 先拿一个 Semaphore 许可
→ 调用 Kafka 异步发送
→ 等 Kafka future 返回结果

为什么 Kafka 发送前还要 Semaphore：

如果 Kafka broker 变慢，异步 send 会产生很多还没完成的 future。没有上限时，本机内存和回调任务会不断堆积。Semaphore 限制“正在等待 Kafka 结果的消息数量”。


四、发送成功怎么走

Kafka future 成功
→ 说明 broker 已按当前配置确认消息
→ 对原 Redis Stream 消息执行 XACK
→ 从 PEL 中移除
→ 尝试 XDEL 清理 Stream 记录
→ 归还 Semaphore 许可

关键顺序是 Kafka 成功以后才 XACK。

如果先 XACK 再发 Kafka：

Stream 认为消息完成
→ Kafka 发送失败
→ Redis 也不再保留待恢复记录
→ 订单事件丢失


五、Kafka 发送失败怎么走

Kafka future 失败
→ 不执行 XACK
→ 消息继续留在 PEL
→ 归还本机 Semaphore
→ 等 recovery 以后重新发送


六、Kafka 成功但进程在 XACK 前死了怎么办

Kafka 已收到消息
→ Java 进程突然退出
→ Redis XACK 没执行
→ 消息仍在 PEL
→ recovery 以后再次发 Kafka

所以同一业务可能进入 Kafka 两次。

这不叫恰好一次，而叫至少一次：宁可重复，不能悄悄丢失。


七、recovery 做什么

定时 recovery 查看 PEL：

读取未确认消息
→ 找出 idle 时间超过阈值的消息
→ claim 给恢复消费者
→ 再次发送 Kafka

idle 表示这条消息交出去以后，多长时间没有得到确认。
claim 表示把失联消费者手里的消息转交给另一个消费者。

投递失败次数超过上限：

从原 Stream/PEL 的处理范围移出
→ 原子写入 dead stream
→ 保存 payload、intentId、源 streamId 等资料
→ 等人工处理或重放

人工重放继续使用原 orderNumber、eventId、intentId，不能生成新的业务身份，否则数据库会把它当成另一笔订单。


八、重复进入 Kafka 后为什么不会重复扣库存

系统目标不是“消息永远不重复”，而是“重复消息不能产生重复业务效果”。

依靠这些稳定身份和约束：

orderNumber：同一订单号唯一。
eventId：同一事件唯一。
intentId：同一次下单意图唯一。
库存流水唯一键：同一库存操作只能记录一次。
订单状态 CAS：状态只能从允许的旧状态推进一次。

重复消息到数据库后：

发现原订单/原流水已经存在
→ 校验这次 payload 与原来是否一致
→ 一致就返回原结果
→ 不一致就报幂等冲突


九、acks=all 到底保证什么

acks=all 表示 Kafka producer 要等待所有“当前同步副本”确认。

它不等于世界上所有副本，也不等于磁盘永远不会坏。

当前本地环境只有：

1 个 broker
副本数 1
min ISR 1

所以 all 实际上还是只有这一个 broker 确认。

enable.idempotence=true 能减少 producer 在同一会话重试时制造的重复，但它也不能解决 Redis XACK 失败导致的整条业务重新发送。

生产通常至少考虑 3 副本、min ISR=2，再根据允许丢多少数据决定配置。


第 6 章：Kafka 消费、MySQL 幂等和库存归属

一、Kafka 消费者收到创建订单消息后做什么

Kafka 把消息交给 CreateOrderConsumer
→ 反序列化订单事件
→ 调用 OrderService.createMq()
→ 先检查订单是否已经存在
→ 调用节目服务，把 Redis 预占落实到节目数据库
→ 节目数据库条件锁座并扣票档余量
→ 节目数据库写库存操作流水
→ 回到订单服务，通过 Spring 代理开启短事务创建订单
→ 全部成功后 consumer 才 acknowledge Kafka offset


二、offset 是什么，为什么要手动提交

Kafka 分区里的每条消息都有位置，offset 就像“我已经读到第几页”。

如果自动提交：

消费者刚拿到消息
→ Kafka 自动把 offset 往后推进
→ 订单还没有写入 MySQL
→ 进程崩溃
→ 重启后从更后面继续
→ 这条订单消息被跳过

手动提交改成：

业务全部成功
→ acknowledge()
→ offset 才推进

异常时不 ACK，而是继续抛给 DefaultErrorHandler 重试。


三、手动 ACK 也会不会重复

会。

订单事务已经提交
→ 还没执行 Kafka ACK
→ 进程退出
→ Kafka 以后重新投递同一消息

所以手动 ACK 不是“不重复”，而是把风险从“业务没做但消息被跳过”变成“业务可能做过，消息再来一次”。后者可以用数据库幂等安全吸收。


四、节目数据库怎么确认这些座位真的归当前订单

不能只根据 seatId 直接更新。

正确条件类似：

座位当前必须是 NO_SOLD
reservation_id 必须为空
programId、seatId 必须匹配

更新成功后：

状态写成 LOCK
reservation_id 写成当前 reservationId
version + 1

请求有 3 张座位，受影响行数必须正好是 3。

只更新了 2 行，说明至少一张已经不符合条件，整个节目库事务回滚，不能创建半份订单。

票档余量也使用条件：

remain_number >= 本次扣减数量

条件不成立就不扣，防止余量变成负数。


五、库存操作流水有什么用

节目库在同一事务里写一条稳定库存流水。

同一 Kafka 消息重试时：

先按 programId + orderNumber 找原流水
→ 找到以后校验 eventId、intentId、reservationId、座位等是否一致
→ 一致说明以前已经完成，返回幂等成功
→ 不一致说明同一个幂等键被配上不同内容，必须报警和拒绝

不能简单看到“订单号存在”就吞掉，因为攻击或代码错误可能拿同一个订单号换一批座位。


六、为什么应用先查订单，数据库还要唯一索引

应用先查：

订单已经存在
→ 快速返回原订单

但两个线程可能同时执行：

线程 A 查不到
线程 B 也查不到
线程 A 插入
线程 B 也插入

所以真正的最后防线是数据库的 orderNumber 唯一索引。

线程 B 遇到 DuplicateKey 后：

重新读取已存在订单
→ 校验 userId、programId、intentId 等身份
→ 一致则当作重复成功
→ 不一致则报冲突


七、订单服务的事务能不能控制节目服务

不能。

订单服务的 @Transactional 只能控制订单数据库连接。
Feign 调用节目服务以后，节目服务使用自己的线程、自己的连接、自己的事务。

实际链路可能是：

节目库锁座成功
→ 回订单服务
→ 订单服务还没创建订单就崩溃

一个 @Transactional 无法把节目库一起回滚。

项目的办法是：

远端节目操作按 reservationId 和库存流水幂等
→ 消息可以重试
→ 对账任务查找“预占成功但订单没创建”等异常
→ 后续恢复或释放


八、重试耗尽后怎么办

Kafka 业务消费失败
→ DefaultErrorHandler 有限重试
→ 仍失败就由 DeadLetterPublishingRecoverer 发到 DLT

DLT 就是 Kafka 死信主题，保存自动处理不了的消息。

DLT 审计需要优先保存：

原始 key
原始 value
headers
源 topic
partition
offset
异常信息

人工重放仍使用原 eventId 和 orderNumber。

DLT 审计容器自己使用专门的无限重试处理，避免审计失败以后继续产生 .DLT.DLT、.DLT.DLT.DLT。


第 7 章：支付、取消、状态 CAS 和可靠迁移事件

一、可靠迁移事件到底在哪里出现

它出现在订单抢到最终状态以后。

支付路径：

支付平台回调成功
→ OrderService.updateOrderRelatedData(orderNo, PAY)
→ CAS 把 NO_PAY 改成 PAY
→ CAS 赢家在同一个订单事务里写 ReservationTransitionEvent=PENDING

取消路径：

延迟取消 worker 发现订单超时
→ OrderService.cancel()
→ updateOrderRelatedData(orderNo, CANCEL)
→ CAS 把 NO_PAY 改成 CANCEL
→ CAS 赢家在同一个订单事务里写 ReservationTransitionEvent=PENDING

因此它不是 Redis 锁座时出现，也不是创建订单时出现，而是订单最终决定 PAY 或 CANCEL 时出现。


二、支付和取消为什么会打架

可能在同一时刻发生：

支付回调：想把 NO_PAY 改成 PAY。
超时 worker：想把 NO_PAY 改成 CANCEL。

不能靠“先查再改”：

支付线程查到 NO_PAY
取消线程也查到 NO_PAY
支付线程写 PAY
取消线程随后写 CANCEL

最终可能互相覆盖。


三、CAS 怎样决定赢家

两边都执行带旧状态条件的 UPDATE：

UPDATE d_order
SET order_status = 目标状态
WHERE order_number = 当前订单号
  AND order_status = NO_PAY;

数据库保证同一行更新时会串行处理。

受影响行数 = 1：自己把 NO_PAY 改掉了，自己是赢家。

受影响行数 = 0：重新读取订单。

已经是自己要的目标状态：同一通知重复到达，算幂等成功。
已经是相反终态：支付和取消冲突，拒绝覆盖。

Redis 分布式锁可以减少同时执行，但最终真相仍由订单数据库 CAS 决定。


四、为什么订单改完还要迁移事件

订单库写成 PAY，只代表订单服务知道已经支付。

节目数据库可能仍然是：

座位状态 LOCK
reservationId 仍存在

Redis 也可能仍然认为座位只是临时锁定。

如果订单事务提交后直接 RPC 更新节目服务：

订单 PAY 已提交
→ RPC 失败
→ 订单已支付，但座位没有变 SOLD

所以 CAS 赢家在同一个订单数据库事务中写一条 PENDING 迁移事件：

订单状态 PAY/CANCEL
+
ReservationTransitionEvent PENDING
→ 两者一起提交或一起回滚

这样只要订单终态存在，数据库里就一定有一条后续待办。


五、事务提交后迁移事件怎么走

订单事务提交
→ 立即尝试派发迁移命令
→ 事件从 PENDING CAS 认领为 PROCESSING
→ 调用节目服务
→ 节目数据库校验 reservationId 和座位状态
→ PAY：LOCK 改成 SOLD
→ CANCEL：LOCK 改成 NO_SOLD
→ 然后 Redis Lua 确认售出或释放
→ 全部成功，事件改 SUCCESS

失败时：

记录错误
→ 增加 attempts
→ 计算下次重试时间
→ 重新进入可重试状态

超过上限：

事件改 DEAD
→ 等人工检查和重放


六、PROCESSING 租约解决什么

worker 认领事件后把它改成 PROCESSING，并写一个处理截止时间。

如果 worker 中途退出：

事件一直 PROCESSING
→ 租约到期
→ 定时任务认为原 worker 失联
→ 用同一个 commandId 再次重试

所以事件不会永久卡死在“处理中”。


七、reservationId 为什么能防 ABA

假设座位最早被 reservation A 占用：

A 超时释放
→ 座位重新可售
→ 后来被 reservation B 占用

这时 A 的一条迟到释放命令到达。

如果只看“座位处于 LOCK”，A 可能误把 B 的座位释放。

正确检查：

座位必须是 LOCK
并且 reservationId 必须仍等于 A

现在 owner 是 B，所以 A 的旧命令不能释放。这个就是 ABA 防护。


八、Saga 用人话怎么理解

不是让订单库、节目库、Redis 同时参加一个超级事务。

而是：

每个服务先完成自己的本地事务
→ 把下一步写成可靠待办
→ 失败就重试
→ 重复执行靠幂等吸收
→ 实在无法完成进入 DEAD 和人工处理

最后让不同系统逐步收敛到一致状态。


第 8 章：lease 延迟取消和数据库扫描兜底

一、订单创建后怎样安排超时取消

订单数据库事务提交成功
→ afterCommit 创建延迟任务
→ taskId 为 order-cancel:订单号
→ dueTime 为当前时间 + 15 分钟
→ 写入 Redis pending ZSET

必须在事务提交后入队，避免订单回滚了但 Redis 里留下取消任务。


二、pending、processing、payload、attempts、dead 分别是什么

pending：还没到时间或等待重试的任务，score 是下次执行时间。
processing：已经被 worker 认领的任务，score 是租约截止时间。
payload：任务内容，例如订单号和节目号。
attempts：已经失败多少次。
dead：超过最大尝试次数，等待人工处理的任务。


三、为什么不能只用一个 ZSET

先从 ZSET 删除，再取消订单：删除后进程崩溃会丢任务。

先取消订单，再从 ZSET 删除：多个 worker 可能重复拿到任务。

所以 claim Lua 原子执行：

从 pending 删除到期任务
→ 放进 processing
→ 写 120 秒租约

这相当于 worker 暂时取得处理权。


四、worker 的完整链路

worker 默认每秒运行一次：

先把 processing 中租约过期的任务重新入队
→ 再从 pending 最多 claim 100 个到期任务
→ 从 payload 读订单号
→ 去 MySQL 查订单

订单仍是 NO_PAY：

调用 OrderService.cancel()
→ 订单 CAS 改 CANCEL
→ 写第 7 章的可靠迁移事件
→ 成功后 ACK 延迟任务

订单已经 PAY 或 CANCEL：

不再修改订单
→ 直接 ACK 延迟任务

这里 ACK 只是清理 pending、processing、payload、attempts，不是 Kafka ACK。


五、处理失败怎么走

业务抛异常
→ fail Lua 从 processing 删除任务
→ attempts + 1

没到 10 次：

按失败次数计算退避时间
→ 放回 pending

达到 10 次：

放进 dead
→ 保留 payload 和 attempts 供人工调查


六、worker 崩溃怎么恢复

任务已经在 processing
→ worker 突然退出，没有 ACK，也没有 fail
→ 等 120 秒租约过期
→ 其他 worker 扫到过期任务
→ attempts + 1
→ 重新放回 pending


七、为什么还要每分钟扫描 MySQL

可能发生：

订单事务提交成功
→ afterCommit 准备写 Redis
→ Redis 宕机
→ 延迟任务根本没有创建

所以订单服务每分钟扫描：

orderVersion = 5
orderStatus = NO_PAY
createOrderTime 已超过 15 分钟

找到以后重新 enqueue。

MySQL 是“哪些订单仍然未支付”的持久事实。
Redis 延迟队列只是让系统更快、更准时地找到到期订单。


八、没有 heartbeat 的边界

租约默认 120 秒，但 worker 处理期间不续租。

如果一次取消执行 150 秒：

worker A 还在处理
→ 120 秒后任务被 worker B 重领
→ 两边可能同时执行取消

业务安全依靠订单 CAS 和远端 reservationId 幂等，但任务层会有重复工作。更完善的做法是 heartbeat 续租，并在 ACK 时校验租约所有者。

当前 delay-cancel-lease.enabled 默认是 false，部署时要显式开启。


第 9 章：分库分表、雪花 ID 和路由基因

一、这一章在下单链路哪里发生

用户提交抢票请求
→ ReferenceOrderOrchestrator 调用 uidGenerator.getOrderNumber(userId)
→ 先生成订单号
→ 再把订单号放进 Redis 预占和创建订单事件
→ 订单服务最终根据这个订单号写入对应分片


二、为什么分库分表

订单都放一张表，数据和访问量大了以后，索引、写入和查询压力都会集中。

当前逻辑相当于：

数据库 0：d_order_0、d_order_1、d_order_2、d_order_3
数据库 1：d_order_0、d_order_1、d_order_2、d_order_3

总共 2 库 × 4 表 = 8 个物理位置。


三、节点为什么先向 Redis 租 workerId/dataCenterId

两台机器可能在同一毫秒生成订单号。为了避免撞号，每个生成节点需要不同身份。

服务启动：

Redis Lua 使用 Redis TIME
→ 清理真正过期的节点
→ 从 1024 个组合中找一个空闲 nodeId
→ 写 ownerToken
→ 设置 120 秒租约
→ 返回 5 位 workerId 和 5 位 dataCenterId

JVM 每 30 秒续租。

发现 owner 不匹配、租约丢失或本地单调截止时间已过：

立即停止生成 ID
→ 防止两台机器共用一个节点编号


四、订单号每一段做什么

0 | 40 位时间 | 5 位数据中心 | 5 位 worker | 7 位序列 | 6 位用户路由基因

40 位时间：区分不同毫秒，从 2024 年开始约可用 34.8 年。
5 位数据中心：区分节点组。
5 位 worker：区分同组机器。
7 位序列：同一生成节点每毫秒最多 128 个订单号。
6 位基因：决定订单落在哪个库表。

一毫秒内序列用完：等待下一毫秒。
发现时钟回拨：拒绝生成，避免撞号。


五、路由基因是什么

就是 userId 最后 6 个二进制位。

生成订单号时，把它原样复制到订单号最后 6 位：

orderNumber 最后 6 位 = userId 最后 6 位

这样用户订单列表按 userId 查询，订单详情按 orderNumber 查询，都能算到同一个物理表。


六、2 库 4 表怎么算

假设用户低 6 位是 001101，也就是十进制 13。

表索引：

13 & (4 - 1) = 1

进入 d_order_1。

低 2 位已经用于分表，所以算库时右移 2 位：

(13 >> 2) & (2 - 1) = 1

最终进入数据库 1 的 d_order_1。

订单号复制了相同的低 6 位，所以按订单号计算仍是数据库 1 的 d_order_1。


七、IN 查询和没有分片键怎样走

WHERE order_number IN (A, B, C)：

分别计算 A、B、C 的目标库表
→ 合并并去重
→ 访问涉及的分片

不能只拿第一个值计算。

查询没有 userId 和 orderNumber：

无法定位
→ 路由到所有库表
→ 汇总结果

跨片排序、分页和聚合因此会变贵。


八、扩容为什么不能只改 YAML

原来 4 张表时，低 2 位决定表。
改成 8 张表后，低 3 位决定表。

历史订单会被新公式算到新位置，但数据还留在旧位置。

真正扩容需要：

准备新库表
→ 新旧路由共存
→ 回填历史数据
→ 双写或 binlog 同步增量
→ 校验新旧数据
→ 读取切到新路由
→ 停止旧写
→ 清理旧数据

路由基因只负责算地址，不负责搬数据。


第 10 章：Caffeine、Redis、MySQL 多级缓存

一、节目详情 V2 的查询链路

请求节目详情
→ 参数校验和 Bloom Filter 检查
→ 查询演出时间
→ 查询节目
→ 查询节目分组
→ 查询分类
→ 查询票档
→ 拼成返回对象

每类数据大致走：

先查当前 JVM 的 Caffeine
→ 命中就直接返回
→ 未命中执行 Cache.get(key, loader)
→ loader 查 Redis
→ Redis 未命中才查 MySQL
→ 写回 Redis
→ loader 返回后 Caffeine 保存


二、Cache.get(key, loader) 解决什么

同一台 JVM 同时有 100 个线程查询同一个节目：

通常只有一个线程真正执行 loader
→ 其他线程等它的结果
→ 不会在本机同时发 100 个 Redis 请求

它只能合并“同 JVM、同 key”的请求。10 台实例仍可能各加载一次，所以 Redis 未命中后还需要分布式锁、二次检查或其他重建保护。


三、缓存击穿

一个热门节目本地缓存和 Redis 同时过期：

大量请求本地 miss
→ Redis 也 miss
→ 一起准备查 MySQL

可以用：

同 key 合并加载
分布式互斥重建
逻辑过期
提前预热
TTL 随机抖动
允许只读接口短暂返回旧值


四、缓存穿透

有人反复查不存在的 programId：

Caffeine 没有
→ Redis 没有
→ MySQL 也没有
→ 下次又完整查询

当前详情入口已经先查 Bloom Filter。

Bloom Filter 说“一定不存在”：直接拒绝，不查数据库。
Bloom Filter 说“可能存在”：继续正常查询，因为它可能误报。

还可以配合参数校验和短期空值缓存。


五、缓存雪崩

大量 key 在相近时间过期，或 Redis 整体故障：

大量请求一起落到 MySQL
→ 数据库连接池被占满
→ 接口延迟继续扩大

可以用：

分散 TTL
Redis 高可用
限流和舱壁
热点预热
只读降级
本地短期旧值


六、多实例本地缓存怎样失效

三台服务实例都缓存了节目 888。

更新 MySQL
→ 删除 Redis
→ 还必须发布“节目 888 已变化”的消息
→ 每一台实例删除自己的 Caffeine

只删 Redis 不够，因为其他实例仍可能从本地返回旧值。

还要确认消息是真正广播给每个实例。如果所有实例在同一个 Consumer Group，一条 Stream 消息通常只会交给其中一个实例，不能天然完成本地缓存广播。


七、当前 TTL 单位错误

DateUtils.countBetweenSecond() 返回秒。

演出还有 3600 秒。

代码却调用：

TimeUnit.MILLISECONDS.toNanos(3600)

于是把 3600 当成 3600 毫秒，也就是约 3.6 秒。本来一小时的缓存缩短了约 1000 倍。

应改成：

TimeUnit.SECONDS.toNanos(3600)

当前 LocalCacheProgramGroup 也有同类问题。

票档本地 TTL 读取 Redis 剩余 TTL 时还要处理：

TTL = -1：Redis key 永不过期。
TTL = -2：Redis key 不存在。
演出时间已经过去。
TTL 太大造成纳秒换算问题。


八、为什么 reservation 不是普通缓存

节目标题缓存丢了，可以查 MySQL 重建。

座位 reservation 表示正在进行的临时归属：

MySQL 可能仍显示未售
Redis 中用户 A 已经临时预占

如果删除 Redis 再按 MySQL 重建，A 的临时归属会消失，用户 B 可能再次占到同一座位。

因此 reservation 是业务状态，不只是查询加速缓存。


第 11 章：Elasticsearch 搜索和降级

一、用户搜索后条件怎样组装

用户选择地区、分类、日期并输入关键词：

areaId、categoryId 使用 term 精确过滤
→ 日期使用 range 范围过滤
→ title 和 actor 使用 match 文本搜索
→ title/actor 放在 should 中
→ minimumShouldMatch(1)，两者至少命中一个
→ 执行 ES 查询

term 适合 ID、状态这类必须完全相等的数据。
match 会对文本分词，适合标题和演员搜索。


二、高亮怎么产生

ES 查询命中后，highlighter 给标题和演员的匹配内容加：

<em>匹配文字</em>

前端再把 em 标签显示成红色或其他强调样式。


三、分页怎样走

当前使用：

from = (页码 - 1) × 每页数量
size = 每页数量

浅分页开销不大。

深分页时，ES 仍要先收集和排序前面的大量结果，再丢掉前面的，只返回最后一页，所以越来越慢。

深分页应限制最大页数，或者使用 search_after。


四、ES 异常以后不同接口怎么走

首页：

查 ES
→ ES 返回空或异常后得到空列表
→ 回 MySQL 查询

分类列表：

查 ES
→ Page 为空
→ 回 MySQL 查询

关键词搜索：

查 ES
→ 异常被 catch
→ 返回空 Page
→ 当前没有同等级 MySQL fallback

所以只能说“部分读取接口可以数据库降级”，不能说 ES 宕机对搜索没有影响。


五、MySQL 和 ES 如何保持一致

MySQL 是业务事实，ES 是搜索副本。

如果直接双写：

MySQL 更新成功
→ 准备更新 ES
→ 进程崩溃
→ ES 仍是旧数据

更可靠的链路：

MySQL 更新
→ 同事务留下变更事件
→ 消费事件更新 ES
→ 失败重试
→ 定时对账找漏同步

当前项目有启动/定时重建 ES 和部分直接删除文档的逻辑，但不等于完整的实时可靠同步。


第 12 章：Spring 事务、线程池、监控和测试

一、@Transactional 正常工作的链路

外部调用 Spring Bean
→ 先经过 Spring 代理
→ 代理开启数据库事务
→ 执行真实方法
→ 成功时 commit
→ 符合规则的异常时 rollback

重点是调用必须经过代理。


二、同类自调用为什么可能没事务

类内部直接调用：

this.createByMq()

这是普通 Java 方法调用，可能绕过 Spring 代理，新的事务配置不生效。

项目在 OrderService 中注入自己的代理对象：

@Lazy
@Autowired
private OrderService orderService;

然后调用：

orderService.createByMq()

完整链路是：

先调用节目服务落实库存
→ 远程调用结束
→ 再通过代理开启订单数据库短事务
→ 创建订单并提交

这样不会在等待 Feign 远程调用时一直占着订单数据库事务和连接。


三、异常被 catch 后为什么可能不回滚

事务方法里：

执行数据库操作
→ 发生异常
→ catch 只记录日志
→ 方法正常返回
→ Spring 代理认为方法成功
→ 提交事务

需要回滚时，应继续抛出异常，或者显式标记 rollback-only。


四、checked exception 和 rollbackFor

Spring 默认主要对运行时异常回滚。

项目经常写：

@Transactional(rollbackFor = Exception.class)

表示普通 checked exception 也触发回滚。


五、新线程为什么不在原事务里

数据库事务连接通常绑定当前线程。

主线程开启事务
→ 把任务提交到线程池
→ 新线程没有自动继承原事务

因此不能认为异步线程和主线程中的数据库修改属于同一个本地事务。


六、本地事务为什么管不了 Feign 远程服务

订单服务 @Transactional 只能管理订单数据库连接。

Feign 调用节目服务时：

节目服务使用另一台机器或另一个进程
→ 另一条线程
→ 另一个数据库连接
→ 自己的事务

所以跨服务要靠远端幂等、可靠事件、重试和对账，不能靠一个 @Transactional 假装全部一起回滚。


七、线程池收到任务后怎样走

当前线程数小于 corePoolSize：新建核心线程。

核心线程已满：尝试进入队列。

队列已满，而且线程数小于 maximumPoolSize：新建额外线程。

队列也满，线程也达到 maximumPoolSize：执行拒绝策略。


八、无界队列为什么危险

核心线程满
→ 新任务一直进入无界队列
→ 队列几乎永远不会满
→ maximumPoolSize 基本没有机会生效
→ 任务等待越来越久
→ 内存可能耗尽

项目公共 BusinessThreadPool 使用容量 600 的有界队列。

Gateway 的 ChannelData 相关线程池当前使用无界 LinkedBlockingQueue，这是一个风险点。


九、线程数为什么不能直接背 CPU 核数 × 2

先判断任务类型。

CPU 计算任务：线程过多会增加上下文切换。
阻塞 I/O 任务：可以多一些线程，但仍受下游连接池限制。

实际确定参数要看：

单任务耗时
允许排队多久
峰值并发
MySQL 连接池
HTTP 连接池
Redis 连接数
下游能承受多少并发

然后再定 core、max、queue 和拒绝策略。


十、拒绝策略为什么要结合业务

普通非关键查询可以快速失败或降级。

核心任务可能选择调用方执行，让上游自然变慢。

必须最终完成的异步任务，不能只丢弃，可以持久化以后补偿。

Stream 到 Kafka 的 ACK 执行器拒绝任务时：

不执行 Redis XACK
→ 消息留在 PEL
→ recovery 后重新投递

这才是拒绝策略和业务可靠性结合。


十一、CompletableFuture commonPool 是什么风险

CompletableFuture.supplyAsync() 不传 executor 时，通常使用公共 commonPool。

如果把阻塞 RPC 放进去：

公共线程被大量阻塞
→ 其他也使用 commonPool 的任务一起变慢

当前主代码没有发现裸用 supplyAsync。KafkaTemplate 返回的 future 完成后，项目把后续 ACK 工作交给专用线程池。


十二、下单慢时按什么顺序看监控

第一步，看 Gateway：

429 是否增加
503 是否增加
舱壁 rejected 是否增加
in-flight 是否顶满
接口 P50、P95、P99 是否上升

P99 表示大约 99% 的请求不超过这个耗时，最慢的约 1% 可能更久。

第二步，看 Redis 预占：

Lua 耗时
座位冲突率
候选重试次数
热点 slot
Redis 慢命令
AOF 和复制延迟

第三步，看 Stream 到 Kafka：

每个 shard 的 lag
PEL 数量
PEL 最大 idle
claim 次数
Kafka 在途数量
send latency/error
dead stream 数量

第四步，看 Kafka 消费：

consumer lag
消费失败次数
重试次数
DLT 数量
订单创建耗时
端到端耗时

第五步，看 MySQL：

连接池是否耗尽
慢 SQL
锁等待和死锁
CAS 冲突率
分片查询是否全路由

第六步，看订单后的库存收敛：

迁移事件 PENDING 数量
超时 PROCESSING 数量
DEAD 数量
超时 NO_PAY 订单数量
订单已支付但座位仍 LOCK 的对账结果

整条下单链路合起来

请求进入 Gateway
→ 清理身份并做 USER、PROGRAM、GLOBAL 令牌桶限流
→ Semaphore 检查当前在途请求是否过多
→ Java 生成候选座位和带路由基因的订单号
→ Redis Lua 全量校验并原子预占座位
→ 同一个 Lua XADD 创建订单事件
→ Stream relay 读取并发送 Kafka
→ Kafka 成功后才 XACK Stream
→ Kafka 消费者先让节目数据库确认库存归属
→ 再用订单数据库短事务创建订单
→ 业务成功后手动 ACK Kafka offset
→ 订单提交后放入延迟取消 lease queue
→ 用户支付或任务超时取消时，用订单数据库 CAS 决定唯一终态
→ CAS 赢家同事务写可靠迁移事件
→ 后台把节目库和 Redis 座位迁移到 SOLD 或 NO_SOLD
→ 延迟队列漏任务由 MySQL 扫描补入
→ 迁移失败、消息失败和库存异常由重试、死信和对账继续收敛
