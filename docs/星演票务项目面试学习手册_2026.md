## 0. 先看结论：这份项目在简历上应该怎么放

原简历的问题不是技术少，而是五个亮点权重接近、字太密，而且把缓存放得太靠前。面试官真正会连续追问的，是“锁座以后怎样不丢单、重复消息怎样不重复扣库存、支付和取消谁赢”。所以新版把可靠性主线放在前四条，缓存与搜索放进学习章节，不抢核心版面。

### 0.1 可直接替换到简历的项目经历

**星演票务｜高并发购票与订单一致性系统**　2025.07—2025.10  
**技术栈：** Spring Boot / Spring Cloud Gateway / Redis + Lua + Stream / Kafka / MySQL / ShardingSphere-JDBC / Caffeine / Elasticsearch

面向热门演出开票时多用户争抢同一座位的场景，围绕入口过载、原子锁座、异步建单、支付取消竞态和分片路由，对购票主链路进行可靠性重构。

- 在 Gateway 实现 USER、PROGRAM、GLOBAL 三维 Redis 令牌桶，并以本机 `Semaphore` 并发舱壁保护下游；下单规则在限流依赖异常时 fail-closed，区分 429 配额拒绝与 503 基础设施异常。
- 将 Java 侧自动配座改为“稳定起点 + 有界分页 + 连座候选”，Lua 只校验最终最多 6 个座位；脚本先全量校验、后统一写入，并在同一原子操作中完成 `AVAILABLE → HELD`、账号限购、幂等回执、到期索引与 Redis Stream `XADD`。
- 以 Redis Stream 消费组中继 Kafka，收到 broker ACK 后才 `XACK`；通过 PEL 超时认领、有限重试、dead stream、Kafka 手动提交与 DLT 构成至少一次投递链路，订单号、事件号、库存流水唯一约束吸收重复消息。
- 在 MySQL 侧以 `reservationId` 条件更新确认座位归属，并用 `WHERE status=NO_PAY` 的 CAS 决定支付/取消唯一赢家；赢家同事务写持久化迁移事件，后台幂等收敛 Redis 为 SOLD/RELEASED，延迟取消采用 lease queue 并由数据库扫描兜底。
- 自定义雪花 ID 将 6 位用户路由基因写入订单号，并修正时间、节点、序列与基因位段重叠；ShardingSphere 自定义算法同时支持 `userId`、`orderNumber` 和多值 `IN` 定向路由，当前为 2 库 × 4 表。

保留前四条，把“雪花 ID + 分片基因”作为替换项：投基础架构/中间件岗就换掉 Gateway；投普通业务后端则保留 Gateway，把分片放到面试口述。

### 0.3 简历上不要这样写

- 不写“Exactly Once”“零丢失”“强一致”。实际语义是至少一次投递、业务幂等、状态 CAS 和最终一致。

## 2. 先建立整条业务链路

### 2.1 一次下单的事实流

```text
客户端 requestId
  → Gateway 清洗伪造身份头，解析可信 userId/programId
  → USER / PROGRAM / GLOBAL 令牌桶
  → 本机并发舱壁
  → 节目、场次、票档、限购校验
  → Java 有界读取 ZSET，生成连座候选
  → 单个 Lua：幂等回执 → 全量校验 → owner/reservation → XADD
  → Redis Stream Consumer Group
  → Kafka broker ACK 后 XACK；失败留 PEL，超限进 dead stream
  → Kafka Consumer 手动 ACK
  → MySQL 按 reservationId 条件锁座、扣票档余量、写库存流水
  → 订单本地事务写订单/购票人/节目快照
  → 支付或超时取消以 status=NO_PAY 的 CAS 决定赢家
  → 赢家同事务写 ReservationTransitionEvent
  → 节目库先幂等迁移，再确认/释放 Redis reservation
  → 对账与告警检查长期偏差
```

### 2.2 这条链路的四个业务不变量

1. **一个座位同一时刻只有一个 reservation owner。** Lua 抢到不等于永久售出；owner 必须绑定稳定 `intentId/reservationId`。
2. **一个请求重试要拿到原结果，不能生成第二份业务。** `requestId + userId + programId` 派生稳定 intent，回执还校验 fingerprint，避免同一幂等键换 payload。
3. **消息允许重复，业务效果不能重复。** Redis PEL、Kafka 重试和 ACK 丢失都会重投，所以数据库必须靠唯一键与条件更新吸收重复。
4. **支付与取消只有一个终态赢家。** 谁先把订单从 `NO_PAY` CAS 到目标状态，谁才有资格写迁移事件；分布式锁只是减冲突，不是最终真相。

### 2.3 90 秒项目介绍逐字稿

> 我这个项目是一个高并发票务系统，我重点重构的是热门演出开票的下单主链路。这个场景最麻烦的不是把接口写出来，而是很多人同时抢同一批座位时，既不能超卖，也不能出现 Redis 锁了座但订单永远没创建，支付和超时取消同时来的时候也只能有一个终态。
>
> 我的处理思路是分三层。第一层在 Gateway 做用户、节目和全局三个维度的令牌桶，再加本机 Semaphore 舱壁，把速率和并发分别控制住。第二层把库存竞争放到 Redis：Java 只做有界候选和连座计算，Lua 校验最终几个座位，先全部校验再统一写，并且锁座和 `XADD` Stream 事件放在同一个脚本里，这样服务就算在脚本返回前退出，也不会出现只锁座没事件。第三层做可靠落库：Stream 只有 Kafka 确认后才 ACK，失败留在 PEL，超限进死信；Kafka 消费端手动提交，MySQL 再用 reservationId、唯一流水和订单唯一键做业务幂等。
>
> 支付和取消这块我没有只靠分布式锁，而是用数据库 `WHERE status=NO_PAY` 的 CAS 决定唯一赢家。赢家在同一事务里写一条持久化迁移事件，后台再把节目库和 Redis 收敛到 SOLD 或 RELEASED。整体语义我会明确说成至少一次加业务幂等和最终一致，不会说 Exactly Once。当前代码的机制测试通过了，但 Docker 还是单节点基础设施，也没有当前主链路的正式压测，所以我不会在简历上写虚构 QPS。

## 3. 技术学习一：Gateway、令牌桶与并发舱壁

### 3.1 为什么要同时限流和限并发

限流控制单位时间允许多少请求，解决的是“来得太快”；舱壁控制正在处理多少请求，解决的是“处理得太慢、请求越堆越多”。即便 QPS 没超，如果下游一次请求从 50 ms 变成 2 s，在途请求也会迅速放大，所以两者不能互相替代。

项目的顺序是：请求校验过滤器先清理客户端伪造的 `userId/code/programId` 头，从 JWT 和已验证请求体派生可信身份；分布式限流过滤器再按 USER、PROGRAM、GLOBAL 依次执行 Redis Lua 令牌桶；最后本机 `Semaphore.tryAcquire()` 做非阻塞舱壁，并在响应 `doFinally` 中释放许可。

### 3.2 令牌桶脚本要会讲什么

令牌桶保存“当前 token 数”和“上次补充时间”。每次请求用当前时间计算应该补多少 token，结果不超过容量；token 足够就扣 1，不够就拒绝。把计算和扣减放在同一个 Lua 中，避免两个网关实例同时读到相同余额。容量允许短时突发，refill rate 控制长期平均速率。

项目对下单采用 fail-closed：Redis 限流依赖异常时返回 503，不让请求无保护地冲击库存。普通查询可考虑 local fallback 或 fail-open，但必须按业务风险配置，而不是全局一个策略。配额耗尽返回 429，依赖异常返回 503，监控含义也要分开。

### 3.3 WebFlux 为什么不能直接跑阻塞 Redis

Gateway 基于少量 Netty event-loop 线程承载很多连接。如果在 event loop 上直接做阻塞 I/O，一个 Redis 慢请求会拖住同线程上的其他连接。代码把阻塞调用调度到 `boundedElastic`，并在外层再做并发限制。要注意 `boundedElastic` 也不是无限资源，生产上更理想的是 reactive Redis、明确超时和隔离线程池。

### 3.4 面试口述

> 我这里不是只说“做了限流”。用户维度防一个账号刷，节目维度保护单场热点，全局维度保护系统总容量；这三个规则顺序执行。令牌桶管速率，本机 Semaphore 管在途并发。下单属于高风险写请求，所以 Redis 限流不可用时我选择 503 fail-closed；如果是详情查询，可以接受局部 local fallback。参数值现在是配置默认值，不是压测结论，真正上线要用目标 QPS、下游连接池和 P99 反推。

## 4. 技术学习二：Redis 数据结构、Cluster 与 Lua 原子预占

### 4.1 v5 为什么不在 Lua 里全场选座

旧做法容易把全量 `HVALS`、JSON 解码、排序和连座搜索塞进 Lua。Redis 脚本原子执行期间会阻塞其他活动，座位越多，热点实例延迟越明显。v5 把工作拆开：Java 从 available ZSET 按稳定 requestId 计算起点，每页最多 64 个，限制候选窗口并生成最多 32 组相邻座位；Lua 只对最终 k 个座位做权威校验，k 又被限制为最多 6。

这里“Java 选候选、Lua 做裁决”很关键：Java 算出来的结果可以过期，所以它不承担正确性；Lua 会再次确认座位仍在 ZSET、owner 不存在、票档和服务端价格一致，竞争失败就换下一组有界重试。

### 4.2 脚本为什么先校验再写

Redis Lua 的原子性表示执行期间其他命令不能插入，不等于传统数据库发生业务错误时自动回滚已经执行的写。如果脚本锁了前两个座位，第三个才发现不可售，就可能留下半份 reservation。因此脚本第一阶段检查所有座位、账号限购、元数据、票档和价格，任何一个失败都在写入前返回；第二阶段才统一 `ZREM`、写 owner/reservation/result/receipt、更新计数与到期索引，并 `XADD` 事件。

### 4.3 为什么同一个 Lua 里还要 XADD

如果 Lua 只锁座，返回 Java 后再发 Kafka，服务可能刚锁完座就 `kill -9`，事件没有任何可靠载体。v5 把 `XADD` 放进同一脚本，让“预占成功”和“出现一条待中继事件”同生共死。请求重试读取幂等回执并返回原订单号，不重复占座。

这不是跨 Redis/Kafka 的原子事务。Redis 自己仍有 AOF `everysec` 最多丢最近约 1 秒写、异步复制故障切换丢最近写等边界。所以准确表达是：消除了应用进程窗口，把剩余风险收敛到 Redis 的持久化与复制上限。

### 4.4 Redis Cluster Hash Tag

Cluster 把 Key 映射到 16,384 个槽，多 Key Lua 必须同槽。项目使用 `stellaris:{sale:<programId % 16>}:program:<programId>:seat:*`，同一个节目预占所需 Key 和对应 Stream 使用同一个 `{sale:n}` Hash Tag。这样脚本可执行，同时把不同节目分散到 16 个 sale shard。

取舍是：一个节目仍然只有一个槽做最终裁决，极热门节目不能靠 Hash Tag 自动横向拆开。要继续扩展，需要按场次/区域拆裁决域、引入排队令牌或单写者，但必须保持“一个座位只有一个权威写者”。

### 4.5 一个容易被忽略的精度问题

Java `long` 座位号可能大于 JavaScript/Lua cjson 可精确表示的 2^53。项目把 seatId、categoryId、ticketUserId 作为字符串序列化给 Lua，再按字符串做 Hash/ZSet member，避免大整数经过 cjson number 后被四舍五入。这个点很适合作为“我确实读了代码”的加分回答。

### 4.6 代码入口

- `ReferenceOrderOrchestrator`：稳定 intent、fingerprint、候选重试、最多 6 张票。

## 5. 技术学习三：Redis Stream 到 Kafka 的至少一次链路

### 5.1 为什么不是普通发布订阅

Redis Pub/Sub 没有离线积压和消费确认，消费者断线期间消息会丢。Stream Consumer Group 会把已投递未确认记录保留在 PEL；消费者退出后，其他实例可以按 idle time claim，适合做短期可靠中继。

### 5.2 成功和失败分别怎样走

实时 relay 对 16 个 sale shard 各启 worker，`XREADGROUP` 阻塞读新消息。publisher 用 `Semaphore` 限制在途 Kafka 发送，避免 broker 变慢时本机无限堆 future。Kafka future 成功后才对原 Stream 执行 `XACK`；Kafka 失败或进程在 Kafka 成功后、XACK 前退出，记录仍在 PEL。

定时 recovery 读取 PEL summary，挑选超过 idle 阈值的消息 claim 到恢复消费者，再次发送。投递次数超过上限后，用原子脚本搬到 dead stream，保留 payload、intentId 和源 streamId，人工重放沿用原业务 ID。

### 5.3 Kafka 成功但 XACK 失败为什么不矛盾

这时同一条业务会再次投 Kafka，所以链路不是“恰好一次”。设计的正确目标是允许重复投递、禁止重复业务效果：Kafka key 用 orderNumber 保证同订单尽量进同分区；订单号、eventId、intentId 和库存流水唯一键让数据库识别重复；状态 CAS 防止重复状态推进。

### 5.4 `acks=all` 到底保证什么

Producer 设 `acks=all`、`enable.idempotence=true`、retries>0、max in flight≤5，能提高 producer session 内重试可靠性并减少重试重复。但本地 Kafka 只有 1 broker、replication factor=1、min ISR=1，所以“all”实际上只有一个副本确认，不能宣称 broker/磁盘损坏也不丢。生产建议至少 3 副本、min ISR=2，再结合业务 RPO 决定。

### 5.5 代码入口

- `RedisOrderCreateRealtimeRelay`：分片 worker 与 `XREADGROUP`。
- `RedisOrderCreatePublisher`：在途许可、Kafka ACK 后才 XACK。
- `RedisOrderCreatePendingRecovery`：PEL idle、claim、投递次数。

## 6. 技术学习四：Kafka 消费、MySQL 幂等与库存归属

### 6.1 为什么消费端必须手动提交

自动提交可能在业务落库前推进 offset，随后进程退出就会跳过消息。项目使用 `MANUAL_IMMEDIATE`：`CreateOrderConsumer` 只有在 `OrderService.createMq()` 成功后才 `acknowledge()`；异常继续抛给 `DefaultErrorHandler`，有限重试后交给 `DeadLetterPublishingRecoverer`。

反过来，业务事务成功但 ACK 前退出会重复消费。这是至少一次的正常现象，所以不能把“手动 ACK”理解为“不重复”，它只是把可能的错误从消息丢失变成可由幂等吸收的重复。

### 6.2 数据库怎样确认座位确实归这个订单

节目库不是看到 seatId 就直接改 LOCK，而是条件更新：座位必须仍为 `NO_SOLD`、`reservation_id IS NULL`，成功后写入当前 reservationId 并递增 version；受影响行数必须等于请求座位数。票档余量也用 `remain_number >= amount` 的条件扣减。

同一事务还写库存操作流水。重复消息先根据 programId + orderNumber 找到原流水，并校验 eventId、intentId 等是否一致；这样既防重复扣减，也防“同一个幂等键带了不同 payload”被悄悄吞掉。

### 6.3 订单创建为什么要先查再靠唯一索引兜底

应用层先查能快速返回已有订单，但并发下两个线程可能同时查不到；数据库 orderNumber 唯一索引才是最终序列化点。完整做法是：发现已有订单就校验 userId、programId、intentId 等身份一致；插入遇到 DuplicateKey 后重新读取并做同样校验，而不是简单吞异常。

### 6.4 本地事务能不能包住远程节目服务

不能。订单服务的 `@Transactional` 只能管理当前线程绑定的订单数据库连接，Feign 调用的节目服务有自己的数据库事务。项目的策略不是假装一个注解能跨服务回滚，而是让远端操作本身幂等，用 reservationId/流水唯一键识别重试，再用后续事件和对账收敛异常窗口。

### 6.5 DLT 当前实现

Kafka 消费端重试耗尽后进入 DLT；项目给 DLT 审计容器单独配置了无限重试处理，避免默认 recoverer 再生成 `.DLT.DLT`。这比旧审计中“毒消息会递归死信”的结论更完善。面试仍应说明：审计存储要优先保留原始 key/value/headers、源 topic/partition/offset 和异常，业务字段只能 best-effort 解析，重放要沿用原 eventId/orderNumber。

### 6.6 代码入口

- `KafkaConsumerReliabilityConfiguration`：手动 ACK、3 次尝试、DLT recoverer、专用 DLT audit factory。
- `CreateOrderConsumer`：业务成功后 ACK，异常继续抛出。
- `OrderService#createMq`：已存在订单校验、远端库存、短事务建单。
- `ProgramService#operateSeatLockAndTicketCategoryRemainNumber`：reservationId 条件更新和库存流水。

## 7. 技术学习五：支付、取消、状态 CAS 与可靠迁移事件

### 7.1 为什么分布式锁不能决定终态

支付回调和超时取消可能同时到达。就算两条路径都加 Redis 锁，仍要面对租约过期、主从切换、某条路径漏加锁等问题。最终真相必须落在订单数据库：

```sql
UPDATE d_order
SET order_status = :target
WHERE order_number = :orderNo
  AND order_status = :NO_PAY;
```

受影响行数为 1 的请求是赢家。受影响为 0 时重新读：已经是同一目标就是幂等成功，已经是另一终态就是业务冲突。代码同时对购票人状态做条件更新。

### 7.2 为什么订单改成功后还要写迁移事件

订单库提交 PAY，不代表节目库和 Redis 已经同步 SOLD。若同步 RPC 失败，直接返回会留下“订单已支付、座位仍锁定”。项目让 CAS 赢家在同一个订单库事务里写 `ReservationTransitionEvent=PENDING`，事务提交后立即尝试派发，定时任务继续捞 PENDING/超时 PROCESSING 重试。

远端迁移命令携带稳定 commandId、intentId 和目标状态：节目库先检查每个座位仍为 LOCK 且 reservationId 相同，再改 SOLD 或 NO_SOLD；重复到达时如果所有座位已经在目标状态，直接幂等成功。随后 Redis Lua 确认售出或释放；旧 reservation A 不能释放后来被 B 占用的座位，这就是 reservationId 的 ABA 防护。

### 7.3 事件表状态机

`PENDING → PROCESSING → SUCCESS/DEAD`。认领用 CAS，PROCESSING 有租约，进程认领后退出不会永久卡住；失败按次数和退避重试，超过上限进 DEAD；人工 replay 仍使用原事件身份。事件表对订单/用户有唯一约束，并校验重复写入的 program、intent 和 target 一致。

### 7.4 口述

> 我把订单终态和跨服务迁移分成两件事。终态由订单库 CAS 决定，保证支付和取消只有一个赢家；跨服务一致性由赢家同事务写的可靠命令负责。这样即使节目服务暂时不可用，订单事实不会倒退，后台可以用同一个 commandId 重试，远端又按 reservationId 幂等，所以最终会收敛。它是可靠事件加 Saga 思路，不是一个跨库大事务。

## 8. 技术学习六：lease 延迟取消与数据库扫描兜底

### 8.1 为什么不能只用一个 ZSET

如果 worker 从 ZSET 删除任务后再取消订单，删除后崩溃会丢任务；如果先取消再删除，多实例会重复执行。项目把任务拆成 pending、processing、payload、attempts、dead：claim Lua 原子地把到期任务移到 processing 并写租约；处理成功 ACK 清理全部状态；失败增加次数并退避，超限进 dead；processing 租约过期会重新入 pending。

### 8.2 为什么还要扫描数据库

延迟任务本身可能在订单提交后入队前失败，Redis 也可能丢最近写。订单服务每分钟扫描仍为 NO_PAY 且超过支付截止时间的订单，再补入 lease queue。数据库是“哪些订单仍需取消”的持久事实，队列只是调度加速器。

### 8.3 当前边界

租约默认 120 秒且没有 heartbeat。如果一次取消处理超过租约，任务可能被另一个 worker 重新认领。业务仍安全的前提是订单 CAS 和库存迁移幂等；但监控上要关注处理时长接近租约，并可增加续租或缩短单任务远程链路。

### 8.4 代码入口

- `DelayCancelLeaseQueue` 与 claim/ack/fail/requeue Lua。
- `DelayCancelLeaseWorker`：先回收过期租约，再 claim；成功 ACK、失败退避。
- `scanDatabaseFallback()`：数据库补扫。

## 9. 技术学习七：分库分表、雪花 ID 与路由基因

### 9.1 订单号位布局

订单号使用：`0 | 40 位时间 | 5 位数据中心 | 5 位 worker | 7 位序列 | 6 位用户路由基因`。6 位 gene 支持 64 个逻辑路由值；7 位 sequence 代表单个生成节点每毫秒最多 128 个订单号，超过后等待下一毫秒；40 位毫秒时间从 2024 epoch 起约可用 34.8 年。

位段必须互不重叠。项目当前通过常量推导 shift，已修复早期 sequence 与 worker/datacenter 重叠的问题。时钟回拨时 fail-fast，不冒险生成可能重复的 ID。

### 9.2 worker/dataCenter 怎样唯一

节点启动后从 Redis 租赁 1024 个组合之一，使用 Redis TIME 减少各 JVM 本地时钟差异；租约约 120 秒、每 30 秒续租，并维护本地单调截止时间。发现租约丢失、owner 不匹配或到期时，ID 生成 fail-closed。它解决节点 ID 冲突，但 Redis 自身的 HA 仍是前提。

### 9.3 为什么 userId 和 orderNumber 都能定向同一片

创建订单时把 userId 低 6 位写入订单号低 6 位。当前 2 库 × 4 表共需要 3 位：低 2 位决定表，再往上的 1 位决定库。按 userId 查询和按 orderNumber 查询提取到同一段 gene，所以都能命中同一物理表。

自定义 complex algorithm 必须处理 `IN` 的每一个值，计算目标集合并去重。项目当前已支持 collection/multi-value，不再只取第一个值。无分片键查询仍会全路由，跨片排序、分页和聚合会放大开销。

### 9.4 扩容为什么不是“改 YAML 就行”

路由基因只负责定位，不会搬数据。扩容通常需要新旧路由共存、存量回填、增量双写或 binlog 同步、校验、读切换、停止旧写和清理；如果直接改变位解释，历史订单会被路由到新位置。面试时主动纠正“只改配置平滑扩容”比硬吹更加分。

- `stellaris-id-generator-framework/.../SnowflakeIdGenerator.java`
- `WorkAndDataCenterIdHandler`、`WorkDataCenterId` 及 Redis lease Lua。
- `stellaris-service-common/.../DatabaseOrderComplexGeneArithmetic.java`
- `stellaris-service-common/.../TableOrderComplexGeneArithmetic.java`

## 10. 技术学习八：Caffeine、Redis、MySQL 多级缓存

### 10.1 查询路径

节目详情 V2 会分别读取场次、节目、节目分组、分类和票档。本机 Caffeine 命中就直接返回；未命中通过线程安全的 `Cache.get(key, loader)` 合并同 JVM 的同 Key 加载，loader 再查 Redis，Redis 未命中才查 MySQL 并回填。票档本地 TTL 读取 Redis 剩余 TTL，使两级失效时间尽量一致。

### 10.2 击穿、穿透和雪崩怎样落到项目

- 击穿：热门节目本地与 Redis 同时过期，大量实例查 DB。可用互斥重建、逻辑过期、提前预热和随机抖动。
- 穿透：不存在 programId 反复查询。可用参数校验、短期空值和 Bloom Filter。
- 雪崩：大量演出相近时间过期或 Redis 整体故障。可用分散 TTL、限流降级、本地旧值和 Redis HA。

本地缓存多实例天然不一致。更新时需要发失效广播或订阅变更事件，每个实例删除 Caffeine；仍要接受传播延迟，并用短 TTL 兜底。库存 reservation 不是普通缓存，不能套“删缓存再查库”思路随意重建。

### 10.3 当前代码缺陷要主动会说

`DateUtils.countBetweenSecond()` 返回秒，但 `LocalCacheProgram` 使用 `TimeUnit.MILLISECONDS.toNanos(...)`，导致节目本地 TTL 约缩短 1000 倍。它主要影响命中率而不是数据正确性，修复为 `SECONDS.toNanos`，并补“演出时间已过、Redis TTL=-1/-2、超长 TTL”的边界测试。这个问题也是为什么缓存不适合放简历第一位。

## 11. 技术学习九：Elasticsearch 搜索与降级

`ProgramEs#search` 用 `term` 做 area/category 精确过滤，`range` 做演出日期区间，title/actor 放在内部 bool `should` 并设置至少命中一个，再用 highlighter 给两个字段加 `<em>`。分页使用 `from + size`，适合浅分页；深分页应考虑 `search_after` 或限制可翻页深度。

首页和分类列表在 ES 返回空时会回 MySQL；搜索接口捕获异常后返回空 Page，没有同等 DB fallback。因此准确说法是“部分读路径支持数据库降级”，不能说 ES 宕机对搜索无影响。索引与 MySQL 的一致性也需通过变更事件、重试和对账，而不是双写接口里两个调用都成功就算完成。

## 12. 技术学习十：Spring 事务、线程池、可观测与测试

### 12.1 `@Transactional` 最常见的坑

Spring 默认通过代理拦截外部调用；同类自调用、private/final 方法、异常被 catch 后不再抛出、checked exception 未配置 `rollbackFor`、新线程以及选错事务管理器，都可能与预期不符。项目把短事务入口通过代理对象调用，并把远程调用与本地提交边界说清楚。

### 12.2 线程池怎样回答才不像背八股

不要先报“CPU 核数 × 2”。先看任务是 CPU 还是阻塞 I/O、单任务耗时、允许排队时长、下游连接池和峰值并发，再定 core/max/queue。队列必须有界；无界队列会让 maxPoolSize 基本失效，把过载变成长延迟和 OOM。拒绝策略不能只说名字，要说明核心任务是快速失败、调用方执行、降级还是持久化补偿。

项目的 Stream publisher 用 `Semaphore` 限制在途 future，relay 每个 shard 有 worker；Gateway 使用 boundedElastic 时也要有舱壁。任何 `CompletableFuture.supplyAsync()` 如果不传 executor，会落到 commonPool，阻塞 RPC 容易污染公共池。

### 12.3 监控指标

- 入口：各维度限流通过/拒绝/依赖异常、舱壁并发与拒绝、接口 P50/P95/P99。
- Redis：Lua 耗时、冲突重试、热点 slot、慢脚本、内存和 AOF/复制延迟。
- Stream：每 shard lag、PEL 数/最大 idle、claim 次数、dead stream 数量。
- Kafka：send latency/error、ISR、under-replicated partition、consumer lag、重试与 DLT。
- 业务：预占成功但订单未创建、NO_PAY 超时量、迁移事件 PENDING/DEAD、库存对账 finding。
- MySQL：连接池、慢 SQL、锁等待/死锁、CAS 冲突率、分片路由扇出。

### 12.4 当前验证结论

2026-08-28 运行定向 Maven 测试，覆盖雪花 ID、延迟取消 lease、订单终态 CAS、迁移事件、Stream→Kafka 失败保留 PEL、预占服务与下单编排，共 25 个测试通过；依赖 Reactor 35 个模块构建成功。这能证明关键机制的单元/组件级行为，不能替代 Redis/Kafka/MySQL 真集群、并发压测和 `kill -9` 故障演练。

## 13. 真实面经高频题：项目逐字稿

这一章的口风参考两份真人资料的共同特点：先把业务背景说清楚，再讲方案和取舍，最后主动交代边界。不是逐句模仿，更不复制原文。正常一问控制在 40—90 秒；面试官追问再展开，别第一次就把所有名词倒出来。

### S01. 你这个项目最大的技术难点是什么？

> 我觉得最大的难点是把一次下单拆成几个存储以后，怎么把每个故障窗口都接住。只防超卖其实不难，Lua 就能做；难的是 Lua 成功后进程挂了怎么办，Kafka 重复怎么办，订单已经支付但节目服务没收到怎么办。
>
> 我最后把它分成三段：Redis 脚本里锁座和 XADD 同时完成，先保证一定留下事件；Stream 到 Kafka 是至少一次，broker 确认后才 ACK，重复由数据库幂等吸收；支付和取消先用订单库 CAS 决胜，再由同事务迁移事件收敛其他服务。这样每一段都有自己的权威事实和恢复者。
>
> 我也不会说它跨存储强一致。Redis 复制和 AOF 仍有最近写窗口，本地 Kafka 又是单副本，所以目前是机制完整、边界明确，还需要真集群故障演练来验证。

**代码落点：** `referenceReserveSeats.lua`、`RedisOrderCreatePublisher`、`OrderService#updateOrderRelatedData`、`ReservationTransitionEventService`。

### S02. 为什么 Lua 能防止超卖？

> 关键不是“Redis 是单线程”，而是同一段脚本里完成了读、判断和写，其他请求不能插进来。两个用户抢同一个座位，第一个脚本确认座位可用后会把它从 available ZSET 移除并写 owner；第二个脚本再检查时就会失败。
>
> 我这里还做了先全量校验、后统一写入。一笔订单最多 6 张，如果第三张不合法，脚本会在任何写操作之前返回，不会锁了前两张留下半单。Java 侧的候选只是建议，真正的并发裁决还是 Lua。

**追问边界：** 长脚本会阻塞 Redis；原子执行不等于 Redis 宕机零丢失，也不等于能和 MySQL/Kafka 一起事务提交。

### S03. Redis 单命令本来就是原子的，为什么还需要 Lua？

> 单条 `ZREM` 或 `HSET` 是原子的，但我的业务是“检查 ready、检查 owner、检查票档和价格、校验限购、移除座位、写 reservation、写回执、写到期索引、XADD”。如果这些命令在 Java 里一条条发，两个请求会在中间穿插，而且网络往返也多。
>
> Lua 的价值是把这组有条件的状态迁移变成一个服务端临界区。它比拿分布式锁包住整段业务更短，但我仍然控制脚本工作量，只检查最终 k 个座位，不在里面扫全场。

### S04. Lua 执行到一半报错会自动回滚吗？

> 不能按 MySQL 事务的回滚来理解。脚本执行期间是原子的，但已经执行的写命令不应该指望业务异常帮你全部回滚。所以我的脚本把可能失败的校验放在前半段，所有座位、价格、owner 和限购都通过以后，才进入统一写入阶段。
>
> 真遇到 Redis 运行时错误时要看错误发生在写前还是写后，并用幂等回执、reservation 和对账判断，不是无脑再执行一遍。

### S05. Lua 成功后服务立刻 `kill -9`，订单会不会丢？

> 旧方案如果 Lua 返回后再由 Java 发 Kafka，确实有“座位锁了、消息没发”的窗口。当前 v5 把 `XADD` 放在同一个 Lua 里，所以只要预占成功，Stream 里就同时出现 eventId 和订单快照。进程在脚本返回前退出，后台 relay 仍能继续中继；客户端重试也会通过稳定 intent 和回执拿到原订单号。
>
> 但我不会回答“绝不会丢”。如果 Redis 主从异步复制时主节点故障，或者 AOF everysec 还没 fsync，最近写仍可能丢。当前方案消除的是应用进程窗口，不是把 Redis 变成共识数据库。

### S06. 为什么用 Redis Stream 中继，不直接发 Kafka？

> 直接发的问题不是 Kafka 不可靠，而是 Redis 预占和 Kafka send 没有共同事务。服务可能刚预占成功就挂。Stream 事件和预占放进同一 Lua，相当于先在 Redis 留下一份待发送事实；后台消费组再发 Kafka。
>
> 选 Stream 是因为它有消费组、PEL 和 ACK，消费者挂了记录不会像 Pub/Sub 那样消失。代价是可靠性上限仍受 Redis 约束，所以我把它叫 Redis-first 可靠中继，不把它说成传统 MySQL Outbox 的完全替代品。

### S07. Kafka 已经发送成功，但 Redis `XACK` 失败怎么办？

> 这条消息会留在 PEL，恢复任务以后还会再发一次 Kafka。这里不要试图追求链路层“只发一次”，因为 Kafka 成功和 Redis ACK 不可能原子提交。
>
> 我的目标是至少一次投递、业务效果一次：重发时沿用原 eventId 和 orderNumber；节目库库存流水、订单唯一索引和状态 CAS 会识别重复。面试官如果问 Exactly Once，我会明确说 producer idempotence 也代替不了业务幂等。

### S08. PEL 里的消息怎么恢复，毒消息怎么办？

> recovery 定时看每个 shard 的 pending，超过最小 idle 时间才 claim，避免抢走还在正常处理的记录。claim 后再投 Kafka；失败次数达到上限，用脚本把原记录搬到 dead stream，不再无限占住 PEL。
>
> 人工重放必须保留原 payload、eventId、orderNumber 和 intentId，先检查下游是不是其实已经成功，再决定重投。坏 JSON 进入 Kafka DLT 时，审计应该先保存 raw key/value/headers 和源 offset，业务字段只能尽力解析。

### S09. `acks=all` 能保证 Kafka 消息绝不丢吗？

> 不能。`acks=all` 只表示 leader 等待当前 ISR 的确认，它能提供的耐故障能力取决于副本数和 min ISR。本地环境只有一个 broker、一个副本，所以 all 也只是一个副本确认，磁盘坏了没有第二份。
>
> `enable.idempotence=true` 主要解决 producer 同一会话重试产生的重复，也不能阻止应用重新 send 同一个订单。生产上我会用 3 副本、min ISR=2，再配合监控 ISR、producer 错误和业务对账，但仍不会说“绝不丢”。

### S10. 为什么 Kafka 消费者要手动 ACK？

> 因为 offset 必须在业务成功以后再推进。先提交再落库，中途退出会丢业务；业务落库后 ACK 前退出会重复，所以后者交给幂等吸收。项目用 `MANUAL_IMMEDIATE`，`createMq` 成功才 acknowledge，异常交给 error handler 重试，耗尽后到 DLT。
>
> 手动 ACK 不是让消息不重复，而是把失败语义变成“可能重复但不丢”，这是我更容易用业务唯一键处理的一类问题。

### S11. 重复消费怎样保证不重复扣库存？

> 我不是用一个 Redis `SETNX` 就说完成幂等，因为标记成功、数据库事务失败也会误判。节目数据库里先查当前 program + orderNumber 的库存操作流水，已有就校验 eventId 和 reservation 是否一致；首次处理时，座位更新带 `sell_status=NO_SOLD` 和 `reservation_id IS NULL` 条件，票档余量也带 `remain_number >= amount`，流水和更新在同一事务。
>
> 订单侧 orderNumber 有唯一约束。应用层先查是优化，唯一索引是最后防线。重复键还要核对 userId、programId、金额和 intentId，不能把不同 payload 吞成“幂等成功”。

### S12. Redis 锁座后，为什么 MySQL 还要再锁一次座位？

> Redis 是开票瞬间的并发裁决层，MySQL 是持久业务事实。Redis 可能重启、故障切换或与数据库短暂不一致，所以消费者落库时不能盲信 seatId，要确认这批座位仍未售，并把 reservationId 写进数据库。
>
> 后面的支付确认或取消释放也必须匹配同一个 reservationId。否则旧订单 A 的迟到取消可能把已经分配给 B 的座位释放掉，这就是常说的 ABA 问题。

### S13. 支付回调和超时取消同时来，怎么保证只有一个成功？

> 我让订单数据库决定，不让 Redis 锁决定。两边都执行 `WHERE order_number=? AND order_status=NO_PAY` 的条件更新，affectedRows=1 的是唯一赢家。输家再读终态：已经和自己目标一样就幂等返回，已经是另一个终态就按冲突处理。
>
> 只有赢家能在同一事务写对应的迁移事件，所以不会同时产生 SOLD 和 RELEASED 两条有效命令。这个地方数据库 CAS 是正确性，分布式锁最多只是降低碰撞。

### S14. 订单已支付，但把座位改 SOLD 的 RPC 失败怎么办？

> 订单改 PAY 和一条 `ReservationTransitionEvent=PENDING` 在同一订单库事务里提交。提交后先立即派发，失败就由定时任务重试；PROCESSING 有租约，执行节点挂了也能重新认领，超过次数进 DEAD 并支持原事件重放。
>
> 节目服务按 commandId 和 reservationId 幂等：先让 MySQL 座位从 LOCK 迁到 SOLD，再确认 Redis；如果重试时已经全是目标状态，就直接成功。这样订单事实不会因为一次 RPC 失败倒退，其他存储最终收敛。

### S15. 延迟取消为什么不用 Redisson 延迟队列或一个 ZSET 就结束？

> 简单 ZSET 最大的问题是取任务和处理之间没有所有权。先删后做会丢，先做后删会重复。项目的 lease queue 把任务分成 pending 和 processing，claim 时原子迁移并写租约，成功 ACK，失败退避，租约过期重新入队，超限进 dead。
>
> 订单创建后入队仍有故障窗口，所以每分钟从数据库补扫过期 NO_PAY 订单。即便任务重复，订单 CAS 和库存迁移幂等也能兜住。当前 120 秒租约没有 heartbeat，处理超过租约可能重入，这是我会继续改的点。

### S16. Redis Cluster 下为什么会 CROSSSLOT？你怎么解决？

> Cluster 用 CRC16 把 Key 映射到 16,384 个槽，多 Key Lua 要求所有 Key 在同一槽。花括号里的 Hash Tag 决定槽，所以我把同一节目 reservation 所需 Key 和 Stream 都放在 `{sale:n}` 下，其中 n 是 programId 对 16 取模。
>
> 这样脚本能执行，也能把不同节目摊到 16 个 sale shard。但一个节目仍在一个槽，这属于正确性和热点拆分之间的取舍。我也只会说 v5 主链路支持同槽，不会说 legacy 全部完成 Cluster 改造。

### S17. 热门节目形成 Redis 热点怎么办？

> 先减少无效流量：静态内容走 CDN，网关按用户/节目限流，下单可增加资格令牌或排队。再减少一次裁决的成本：Java 有界选候选，Lua 只查最多 6 个座位，避免大 Key 全量扫描。
>
> 如果单节目还是超过一个 Redis 主节点的写能力，就按场次、看台或区域拆独立裁决域，或者引入分区单写者。不能简单把一个座位复制到几个分片同时写，因为“一个座位只有一个裁决者”这个不变量会被破坏。

### S18. 订单号为什么要带用户基因？

> 因为有些查询只有 orderNumber，没有 userId。如果订单号低 6 位复制 userId 低 6 位，分片算法从两者都能取到同一个 gene，直接定位 2 库 × 4 表，避免全库路由。
>
> 代价是 ID 布局和分片拓扑耦合。我会把位段画出来：40 位时间、5+5 节点、7 位序列、6 位基因。序列每节点每毫秒 128 个，节点 ID 由 Redis 租约分配，时钟回拨就拒绝生成。扩容也不能只改 YAML，还要迁数据和兼容历史路由。

### S19. 分库分表后 `IN` 查询怎么路由？

> 自定义 complex algorithm 要对 `IN` 中每个值分别计算目标库表，再对结果去重。只看第一个值会直接漏订单，特别是对账一次批量查很多订单号时很危险。
>
> 项目当前已经支持 collection/multi-value。无分片键仍会全路由；跨片排序和分页要各分片取候选再归并，深分页成本很高。分片解决的是单表容量和并行，不是让所有 SQL 自动变快。

### S20. 你的项目 QPS 多少？

> 我不会给一个没有同口径证据的数字。仓库里有历史 JMeter 报告，但不是当前 v5 主链路、也没有完整记录机器、数据量、预热、并发模型和订单最终落库完成点，所以我没有把它写进新版简历。
>
> 当前我能证明的是 25 个关键机制测试通过，35 个 Reactor 模块构建成功。下一步可信压测会同时给入口吞吐、下单成功率、P95/P99、Stream/Kafka lag、订单最终落库吞吐、数据库连接池和错误率，并说明 Kafka 单副本环境的限制。比起背一个好看的 QPS，我更愿意把测量口径说清楚。

## 14. 高频基础追问：短答版

### A01. Redis 为什么快？

核心数据在内存，数据结构针对常用操作优化，事件驱动减少线程切换，单命令路径短。但大 Key、长 Lua、`KEYS/HVALS`、慢网络和持久化抖动仍会阻塞事件循环；“单线程”不是永远快。

### A02. RDB 和 AOF 怎么选？

RDB 是时点快照，恢复快、文件紧凑，但两次快照间写入可能丢；AOF 记录写命令，耐久性取决于 fsync 策略，everysec 通常仍有最近约 1 秒窗口。重要库存不能只靠“开了 AOF”，还要副本、业务幂等和对账。

### A03. 缓存穿透、击穿、雪崩分别是什么？

穿透是不存在数据反复打 DB；击穿是单个热点过期；雪崩是大量 Key 同时失效或 Redis 整体故障。对应空值/Bloom、互斥重建/逻辑过期、随机 TTL/限流降级/HA。库存状态机 Key 不是普通缓存，不能随便删后重建。

### A04. producer idempotence 和业务幂等有何区别？

Producer idempotence 用 PID/sequence 去重同一 producer session 的重试批次；应用主动再发、重启后重放、Stream relay 重发仍可能重复。业务幂等靠 eventId/orderNumber、唯一约束和状态 CAS。

### A05. Kafka 为什么吞吐高？

顺序追加日志、批量发送、页缓存与零拷贝思路、分区并行共同提升吞吐。回答项目时还要说代价：批量会增加等待，分区只保证分区内顺序，副本和 ISR 配置决定耐故障能力。

### A06. Kafka 如何保证同订单有序？

用 orderNumber 做 key，使同订单进入同一 partition；Kafka 只保证 partition 内顺序。扩分区可能改变映射，迟到消息也存在，所以订单状态仍用合法迁移 CAS，不能只依赖到达顺序。

### A07. 什么是 MVCC？

InnoDB 通过 undo 版本链和 Read View 为普通一致性读提供快照；当前读和 UPDATE/DELETE 仍要加锁。RR 下讨论幻读必须区分快照读与锁定读，不要一句“MVCC 没有幻读”结束。

### A08. 乐观锁和悲观锁怎么选？

冲突低、临界区短时，version/status CAS 的乐观锁吞吐更好；冲突高且必须先读后改时可用 `SELECT ... FOR UPDATE`。远程支付不应持数据库锁，项目用短事务 CAS 决定终态。

### A09. 唯一索引为什么是幂等最后防线？

应用“先查再插”有并发窗口；唯一约束在数据库内序列化冲突。捕获 DuplicateKey 后要重新读取并核对 payload，不能只吞异常。

### A10. Spring 同类调用为什么可能让事务失效？

默认事务基于代理，`this.method()` 没经过代理就不会触发拦截。private/final、异常被吞、checked exception 未指定 rollback、异步线程和选错事务管理器也要检查。

### A11. 为什么远程调用不能加入本地事务？

Spring 本地事务绑定当前线程和当前资源，HTTP/Feign 到另一个进程不会自动传播同一个数据库事务。跨服务用幂等命令、Saga/TCC、可靠消息和补偿，不要用一个 `@Transactional` 假装跨库原子。

### A12. 线程池参数怎样定？

从任务 CPU/IO 比例、耗时、下游连接池、目标延迟和峰值并发反推。队列要有界，拒绝策略要与业务补偿匹配；阻塞任务不要扔 commonPool。没有运行数据时只给估算和调参方法，不报万能公式。

### A13. `volatile` 能保证什么？

保证可见性和一定的有序性，volatile 写 happens-before 后续读；不能保证 `count++` 这种读改写复合操作的原子性。

### A14. `synchronized` 和 `ReentrantLock` 怎么选？

两者都提供互斥与可见性。Lock 支持可中断、超时、公平和多个 Condition，但必须 finally 解锁；synchronized 更简单、JVM 优化成熟。项目正确性仍主要依靠 Lua/CAS，不靠 JVM 锁跨实例。

### A15. Caffeine 为什么能缓解击穿？

同一 JVM 的 `cache.get(key, loader)` 会合并同 Key 的加载，避免本机很多线程同时回源。但多实例之间不能合并，所以 Redis 层仍需互斥重建/预热，更新还要广播失效。

### A16. Elasticsearch 的 term 和 match 有什么区别？

term 做未分析的精确值过滤，适合 area/category；match 会经过分析器，适合标题和演员关键词。项目把 title/actor 放 should 并至少命中一个，再做高亮。

### A17. ES 宕机怎么降级？

项目首页和列表在 ES 空结果时回 MySQL，搜索接口目前只返回空 Page，没有同等降级。生产上应区分“真正无结果”和“ES 异常”，限制 DB fallback 查询范围，避免故障时把流量全部打到 MySQL。

### A18. 如何排查 P99 突然升高？

先按 trace 拆网关、Lua、Stream/Kafka、消费落库和下游 RPC；同时看限流、舱壁、线程池队列、GC、Redis slowlog/热点、Kafka lag/ISR、MySQL 连接池和锁等待。先定位延迟在哪一段，再看该段资源和最近变更，不要上来就加机器。

### A19. 怎么证明系统不超卖？

不能只跑接口看 200。并发抢同一组座位，断言成功数不超过库存、owner/reservation/available/sold 集合互斥、MySQL 锁座数和订单数一致；再注入 Kafka 重复、ACK 丢失、pay/cancel barrier 和进程退出，观察最终状态和对账 finding。

### A20. 如果让你重做，先改什么？

第一补真集群故障演练和当前主链路压测，建立可证明的容量与恢复时间；第二修节目本地缓存 TTL 单位并补搜索降级；第三给延迟任务增加 heartbeat/租约监控，再完善跨分片扩容迁移工具。正确性和证据优先于继续堆中间件。

## 15. 面试官继续拷打时的场景题

### D01. 设计一个热门演出开票系统

> 我会先问四个条件：是否选座、单人限购、支付超时时间和目标容量。然后按流量从外到内设计。静态资源走 CDN，详情走多级缓存；Gateway 按用户、节目和全局限流，再用舱壁限制在途请求。真正锁座按场次或区域划分唯一裁决域，Java 做有界候选，Redis Lua 原子预占并留下事件。
>
> 下单落库采用至少一次：可靠中继到 MQ，数据库用 reservationId、唯一键和 CAS 幂等；支付与取消以订单库终态为准，可靠事件迁移座位；延迟取消有 lease/DLQ/数据库补扫。最后补监控、对账和降级。讲完正常流程，我会专门补三个故障窗口：预占后进程挂、MQ 重复、支付成功但迁移失败。

### D02. 如果 Redis 也扛不住怎么办？

> 我不会只回答“加集群”。同一个热门节目本质上仍是单热点，先用资格令牌/排队层、程序维度限流和快速失败减少到达裁决层的请求；再缩短 Lua、压缩 value、避免全场扫描。如果仍超限，按场次、看台或区域拆成互不重叠的座位裁决域，或者每个分区用单写者顺序处理。
>
> 拆分的底线是一个座位只能归一个分区，不能为了扩展把同一库存复制成多个可写副本。

### D03. 设计 pay/cancel 并发测试

> 先造一个 NO_PAY 订单，用 barrier 让支付确认和取消同时起跑，循环跑很多次并随机给远程迁移加延迟。断言订单 CAS 只能一方 affectedRows=1，迁移事件只有一条有效目标，购票人、节目库座位和 Redis 最终状态与订单一致。
>
> 还要分别模拟赢家事务提交后进程退出、迁移 RPC 成功但本地标记失败、同一回调重复到达。只看两个接口都返回 200 没意义，必须查最终事实和事件重试状态。

### D04. 设计一次可信压测

> 先固定代码版本、机器、JVM、Redis/Kafka/MySQL 拓扑、数据量和预热方式。负载要分详情查询、同一热点节目下单、多个节目混合下单，requestId 的唯一/重试比例也要明确。入口响应和最终订单落库是两个完成点，要分别统计。
>
> 输出吞吐、成功率、P50/P95/P99、资源利用率、Lua 耗时、PEL/Kafka lag、数据库连接池与锁等待；逐级加压找到首个饱和点，再做 broker 变慢、消费者停机、Redis 主节点故障等演练。数字必须带环境和口径，不能把一次 JMeter 截图当结论。

### D05. 设计对账，不只比库存总数

> 数量相等不代表集合相等。我会检查 meta 是否等于 available、owner、sold 的并集，三个集合是否互斥；reservation 中每个 seat 是否都属于同一 intent；订单 PAY/CANCEL 是否对应 SOLD/RELEASED；Stream/dead、Kafka DLT、库存流水和订单的 eventId、金额、版本是否一致。
>
> 对账先报告和安全重放，事实不明确时不自动放座。每个分片保存稳定游标和 last success，finding 持久化并区分自动修复、告警和人工处理。

## 17. 真人口述模板

遇到没背过的项目题，按下面五句组织：

1. **背景：**“这个问题出现在……，如果不处理会……”
2. **选择：**“我这里没有直接用……，而是把它拆成……”
3. **落地：**“代码里由 A 保存事实，B 负责投递，C 用唯一键/CAS 兜底。”
4. **失败：**“如果刚好在 X 和 Y 中间退出，会……，恢复者是……”
5. **边界：**“它保证的是……，不保证……；真上生产还需要……”

一个示例：

> 这个问题出现在 Redis 已经锁座、但订单还没落库的窗口。如果直接在请求线程发 Kafka，进程退出可能只锁座没消息。所以我把预占和 XADD 放进一个 Lua，Stream relay 再至少一次发 Kafka；重复由订单号、库存流水和 CAS 吸收。如果 Kafka 成功但 XACK 失败会重发，这是设计允许的。它保证的是应用窗口可恢复，不代表 Redis 故障切换零丢失。
