# Stellaris 交易架构：单交易库 + Redis Stream

日期：2026-09-10。

状态：核心代码已于 2026-09-11 按本方案实施；DDL 仅作为新环境初始化资产，未对现有数据库执行；完整故障演练和容量测量仍待进行。本文是当前实现的设计基线，已删除此前包含 `t_ticket_stock` 的冲突草案。

## 1. 目标与最终决定

保留现有抢票项目的并发治理、Lua 原子预占、消息幂等和支付状态竞争能力，减少中间件、重复库存数据以及跨库补偿。

确定采用以下方案：

- 保留 Redis Lua + Stream，订单服务直接消费 Stream，移除创建订单链路的 Kafka 中继。
- 核心销售数据使用一个 MySQL 交易库，订单服务采用普通 Hikari 数据源，退出 ShardingSphere 路由。
- **取消 `t_ticket_stock` 整张表。座位行就是库存，余票由座位状态派生。**
- 请求结果、账号限购、座位销售状态、订单和明细在同一个本地事务内提交。
- 支付、取消涉及的订单与销售库存状态在同库事务内更新；Redis 通过持久化同步记录收敛。
- 移除 Redis 延迟取消队列，数据库到期扫描直接驱动关单。
- 后台职责限定为：Stream 消费及重领、数据库到期关单、Redis 同步重试。
- 保留一份异常消费审计和显式处理入口，不同时维护 Stream dead 与 Kafka DLT 两套机制。

本轮业务范围为按座位售票、每单同一场次、单笔最多六张票。可售集合由交易库中初始化的可售座位确定，不引入独立票档配额、跨场次订单或退款后的自动返售规则。

## 2. 主链路与用户承诺

```text
Gateway：鉴权、限流、本机并发保护
    ↓
Program：校验场次与请求，提供候选座位
    ↓
Redis Lua：请求幂等 + 快速限购 + 精确预占 + XADD
    ↓
返回“处理中”，携带稳定 requestId / reservationId / orderNumber
    ↓
Order：直接消费 Stream，有界读取和有界并发
    ↓
MySQL 单个本地事务：
请求幂等 + 最终限购 + 全部座位 CAS + 订单及明细 + 请求成功结果
    ↓
事务提交后 ACK，按已处理消息 ID 清理源记录
    ↓
前端查询持久化结果，显示“待支付”或明确拒绝原因
```

Redis 预占成功表示受理，MySQL 提交后才表示订单创建成功。同一请求重试必须使用原请求号和相同业务参数；服务端返回原结果，不重新选座或换号创建第二笔订单。

临时查无订单、查询失败和明确创建失败必须区分。预订结果查询统一读取请求处理结果，查询订单成功时再返回订单状态。提交结果未知时继续凭原请求身份确认，不直接取消或释放座位。

## 3. 服务和中间件范围

| 对象 | 本轮处理 |
| --- | --- |
| Gateway、用户、节目、订单、支付等服务外壳 | 保留，不同时重写所有周边业务 |
| Program | 管理节目、场次、票档介绍、座位布局；销售状态退出该服务的写入职责 |
| Order | 统一管理销售库存、请求结果、账号额度、订单和订单状态转换 |
| Pay | 保留现有支付接入与退款能力；与订单服务的外部调用不放进数据库事务 |
| `stellaris-migrate-service` | 订单扩容迁移服务退出默认运行主线，历史实现作为演进材料保留 |
| MySQL | 核心交易使用一个库、同一事务管理器和同一事务连接 |
| Redis | 保留预占、Stream、缓存和限流用途；按用途分别计量容量 |
| Kafka | 创建订单中继、消费者、DLT 退出主线；网关埋点改结构化日志后，移除默认启动依赖 |
| Elasticsearch | 搜索选配，不参与交易正确性 |
| Nacos | 保留既有服务发现和配置能力 |
| ShardingSphere | 从订单交易链路移除；Program、Pay、User 自身分片本轮不动 |

订单号的新生成路径停止嵌入路由基因，保留 Snowflake 与 Redis 租约校验。存量订单号保持不变。生成器切换需要验证新旧号码不会碰撞、调用仍经过租约检查；订单号描述为唯一、趋势递增，不承诺全局严格有序。共享发号接口和公共依赖不能仅因订单服务不再分片就整包删除。

## 4. 数据归属与 Schema 设计要求

以下为目标表职责、关键列与约束，正式字段类型、外键取舍和迁移 DDL 在第一阶段产出中核对现有表后落实。本轮不执行 DDL。

### 4.1 `t_seat_inventory`：唯一销售库存事实

```text
program_id
seat_id
ticket_category_id
sell_status          AVAILABLE / LOCKED / SOLD
reservation_id       当前锁定或售出的预订归属
order_number         当前归属订单
version              销售状态版本
price_in_cents       开售时的服务端价格快照
sale_version         已发布销售配置版本

PRIMARY KEY (program_id, seat_id)
INDEX (program_id, ticket_category_id, sell_status)
INDEX (order_number)
```

价格与销售版本快照用于在交易库内验证消息，避免事务中跨库读取价格或信任客户端金额。座位布局仍归节目库；开售后不得任意修改已发布的布局、票价和销售范围。

一笔订单按固定座位顺序执行条件更新：只有 `AVAILABLE` 且符合场次、票档、价格版本等条件的座位，才能绑定本次 reservationId/orderNumber 并变为 `LOCKED`。每个指定座位都必须成功，任何部分失败整单回滚。不额外扣减票档计数。

### 4.2 `t_account_program_purchase`：权威限购额度

```text
program_id
user_id
purchase_count       当前有效锁定与已购票数
updated_at

PRIMARY KEY (program_id, user_id)
```

计数行首次使用时幂等初始化。限购上限来自已发布的服务端规则，`0` 表示该场次未配置账号上限，但仍累计有效购买数；正数上限在事务内通过条件更新校验影响行数，禁止用请求传入的上限放宽规则。取消时只由状态转换赢家返还额度，防止重复扣减。

Redis `account-count` 是前置快速拒绝信息；数据库计数是最终裁决。短暂不同可能造成提前拒绝或数据库最终拒绝，通过预订释放、终态同步和受控重建收敛。移除票档共享计数行后，同账号额度行、热门座位和索引仍可能发生竞争，不能宣称不存在热点。

### 4.3 `t_order_request`：持久化请求结果

```text
reservation_id       VARCHAR(64)，主键，对应 Lua intentId
program_id
user_id
request_id
order_number         BIGINT NOT NULL
request_fingerprint  业务请求摘要
result_status        CREATED / REJECTED
reject_code
created_at

PRIMARY KEY (reservation_id)
UNIQUE (user_id, request_id)
UNIQUE (order_number)
```

当前系统在预占之前生成订单号，因此拒绝结果也保留预分配订单号；没有正式订单行不代表没有申请对应的号码。前端凭原号码或请求号应能查到拒绝结果。

摘要必须覆盖用户、场次、购票人、选座/票档及数量等决定业务含义的参数，并明确自动选座请求的稳定摘要口径。唯一键冲突后核对请求身份与摘要，不能无条件当作成功并 ACK。

该表在消费端生成，不增加 Redis 预占之前的 MySQL Intent 写入，不设计独立的跨存储建单意图状态机。

### 4.4 复用的数据

- 订单、购票人明细和节目关联全部进入同一交易库，保留前端和支付接口所需业务快照。
- 订单持久化到期时间，增加适用的 `(order_status, expire_time, id)` 索引用于到期扫描；不能只按新配置重算旧订单期限。
- `d_reservation_transition_event` 退出分片，职责缩小为 Redis 待同步记录。按订单与状态版本等稳定业务键去重，保存目标状态、预订归属、重试进度和错误信息，不再修改节目库销售数据。
- 异常消费记录表改成 Stream 来源，保存 stream key、消息 ID、原始 payload、失败原因和处理状态。Kafka topic/partition/offset 等专属逻辑退出；无法解析业务身份的消息也必须可以留存。
- `order_inventory_operation` 在旧跨服务库存调用退出、切换核对完成后清理。

## 5. 事务、幂等与状态契约

### 5.1 消费创建订单

1. 在同一交易库事务内通过请求唯一约束取得本次处理权；重复请求读取并验证已提交结果。
2. 校验业务截止时间、销售快照和最终限购额度，按固定顺序锁定全部指定座位。
3. 写订单、明细、关联及 `CREATED` 请求结果，一起提交；事务内不调用远程库存、用户或支付服务。
4. 提交成功后确认消息。若提交结果未知，通过原请求查询或重试确认。
5. 临时数据库错误回滚并保留 Pending，暂停/退避重试。明确业务拒绝在回滚后用短事务记录 `REJECTED` 和 Redis 释放任务；该记录与成功记录竞争同一请求唯一键，不能覆盖已成功结果。
6. 持久化成功、拒绝结果或异常审计后才能 ACK。无法判断的消息保留证据，禁止把未知结果当成可安全释放。

允许重复投递；只允许一个业务结果。不能把“先查再插”作为唯一幂等措施。已提交拒绝结果的请求不能被迟到或重放消息重新建单。

### 5.2 正常状态转换

| 动作 | 座位 | 账号额度 | 同事务操作 |
| --- | --- | --- | --- |
| 创建待支付订单 | AVAILABLE → LOCKED | +k | 请求结果、订单、明细和全部座位一起提交 |
| 支付成功 | LOCKED → SOLD | 不变 | 订单支付状态、座位和 Redis 待同步记录一起提交 |
| 未支付取消 | LOCKED → AVAILABLE | −k | 订单取消状态、座位、额度和 Redis 待同步记录一起提交 |

支付和取消通过订单状态条件更新竞争，只有赢家执行座位和额度变化。确认、释放同时检查 reservationId/orderNumber 与状态，旧请求不能改变后来订单的归属。

真实支付采用已有支付/退款接入。查单和渠道关单在数据库事务之外；未知支付结果保留待处理状态，晚到支付按明确的状态机和稳定退款号处理。本轮不新增退款后自动恢复库存或额度的销售规则。

## 6. 余票读路径和预热

### 6.1 余票读取

- 用户展示：读取已就绪库存的 available ZSET `ZCARD`，保留 VO 的 `remainNumber` 名称与返回形状。
- 管理核对：按场次和票档聚合交易库 `AVAILABLE` 座位，低频执行，避免进入每笔下单热路径。
- Redis 已预占而数据库未提交时，两个数量可以暂时不同；缓存同步滞后也会影响差值，不能将所有差异直接判定为库存错误。
- 用 ready/销售版本区分未预热与售罄。已就绪且可售集合为空时返回零；未就绪或 Redis 不可用时按统一契约降级，不伪装为确定售罄，也不无界回源。
- 静态 `totalNumber` 在发布时与实际销售座位集合核对。旧 `remain_number` 字段停止业务读写，切换完成后再清理。

需要覆盖的改造位置包括：

| 位置 | 处理 |
| --- | --- |
| `TicketCategoryService.getRedisRemainNumberResolution` | 更换余票数据源，清理旧 HASH 回填逻辑 |
| `TicketCategoryService.detail / selectList / selectListByProgram` | 停止通过实体复制泄露旧余票值，统一填充派生余票 |
| `ProgramManageService` | 数据库余票改为聚合，Redis 余票改读新模型 |
| `TicketCategoryMapper` 与 XML | 删除旧 reduce/increase/batchUpdate remain 写入及对应调用 |
| 建票档 DTO、实体、初始化逻辑 | 删除余票输入语义，核对展示总量与销售座位集合 |
| Program 管理修复、对账与旧缓存清理 | 移除旧计数校正，改查新销售事实与同步进度 |
| 正确性测试、初始化/重置/压测脚本 | 替换对旧分片库和 remain_number 的断言与更新 |

按当前源码搜索，前端没有直接引用该字段，ES 检索字段中未发现余票依赖；仍需接口回归验证，不能仅凭字段名保留就跳过测试。

### 6.2 首次初始化与重建分开

首次准备采用：冻结布局与销售版本 → 幂等初始化交易库销售座位 → 核对数量和归属 → 构建 Redis → 校验完成后开闸。同版本重入只校验或补齐合法的未完成初始化，不重复增加额度或覆盖已交易座位。

已有交易时，Redis 重建以交易库当前 LOCKED/SOLD/AVAILABLE 状态为准，不能从静态布局重新把全部座位置为可售。维护约束覆盖入口、消费者、支付和关单等库存写入；处理在途工作并取得一致快照后重建。首版使用受控维护窗口，不引入无感双版本切换。

## 7. 三类后台职责

### A. Stream 消费与 Pending 重领

单消费组、有界拉取、有界执行并发。第一版每单独立数据库事务；批量读取与按已完成 ID 批量 ACK 可以使用，不预先引入跨订单大事务。

进程退出留下的 Pending 通过超时重领恢复。认领不代表旧执行者停止，数据库必须承受并发重复消费。按实际处理超时设置重领参数，不沿用 Kafka 发送超时假设。基础设施停机采用退避、暂停消费或入口背压，不快速耗尽次数制造大量死信。

### B. 数据库到期关单

按索引分批读取到期订单，直接执行关单业务。多实例通过条件更新或短事务认领协作。移除 Redis lease/ACK 延迟队列和数据库扫描重新入队路径。

### C. Redis 待同步重试

数据库事务内留下同步依据，提交后尽快执行 Redis 更新；失败由该记录驱动退避重试。同步脚本按预订归属和版本幂等执行，不修改第二个业务数据库。数据库已提交的交易事实不因缓存同步失败回滚。

超过自动处理范围的任务保留状态、错误与显式处理入口。诊断工具可以核对订单、座位、消息和同步记录，不另外实现一套自动补偿状态机。

## 8. 容量与可靠性边界

- Redis 预占过滤大量无效争抢，交易库还会处理重复消费、支付、关单等工作。库存数量不能直接推出每秒写入容量。
- 单场节目仍在一个 Redis 槽，增加 Cluster 主节点不能直接把单场吞吐乘以节点数。本轮不做会破坏跨座位和限购原子性的场次内跨槽拆分。
- 移除 Kafka 后，Stream 消息等待数据库处理期间留在 Redis；消息停留时间、Pending、回执、异常记录和多场同时销售都纳入容量测量。
- 根据积压数量、最老消息年龄、内存和数据库处理延迟设置经验证的接单阈值。限流 Redis 本身承受的流量也纳入测量。
- 不使用无视 Pending 的 `XTRIM MAXLEN` 删除可靠队列内容。批量 ACK 降低调用开销，不代表逐消息处理成本消失。
- Lua 成功执行提供原子隔离；运行时错误不具备 SQL 回滚语义，写前校验参数、键类型和配置。
- MySQL 提交前的受理记录仍依赖 Redis 持久化与复制，不能承诺绝对零丢失；Redis 故障时暂停接单并按维护流程恢复。
- 消除的是订单、座位、账号额度之间的跨业务库提交窗口。Redis 同步与支付渠道仍存在独立系统边界。
- 单交易库是逻辑事务归属，不等于生产只部署一台数据库机器；持久化、复制、备份与切换需要另行验证。

## 9. 分片退场与后续演进 ADR

第一阶段补充 ADR：采用单交易库使锁座、限购和建单形成一个本地事务；订单服务去掉分片路由，历史 SQL、路由算法、路由基因和扩容材料作为历史设计保留，不包装成新版本运行能力。

先优化索引、事务、慢查询和数据库容量配置，再根据瓶颈评估归档与读写分离。幂等裁决、支付关单和刚创建订单的确定性查询走主库。

分区表是单独评估项，不作为必经步骤。MySQL 分区列必须包含在每个唯一键中，按时间分区可能影响订单号和请求号的唯一性约束。归档同样必须保留足够的幂等结果或终止记录，不能让历史消息重放变成新的请求。

真正达到单库写入瓶颈后，再评估按场次等交易维度分片；一张订单的销售数据必须在同一物理分片，不恢复按用户拆订单、按节目拆库存的旧边界。触发阈值标为待实测确定，不预写 QPS。

## 10. 实施顺序与交付物

| 阶段 | 工作 | 交付与切换约束 |
| --- | --- | --- |
| 1 | Schema、唯一键、事务、状态转换、查询契约、分片退场 ADR | 只做设计产出；不改运行代码、不执行数据库变更 |
| 2 | 独立验证环境中的单交易库、销售数据初始化和预热 | 数据初始化可重入；原运行链路仍保留 |
| 3 | Stream 直连消费与单订单事务 | 验证幂等、限购、整单锁座和明确失败结果 |
| 4 | 支付/取消同库 CAS、数据库到期关单、Redis 同步 | 新链路的创建与终态处理形成完整闭环 |
| 5 | 查询、管理、测试脚本和初始化资产更新 | 接口形状兼容，清理旧余票依赖，完成只读诊断 |
| 6 | 故障演练与四组测量 | 保存命令、环境、原始报告和业务不变量核对结果 |
| 7 | 受控切换并清理旧入口、默认依赖和文档 | 新旧写入不能同时操作同一批座位 |

切换前关闸、停止旧消费者、处理或留存未完成请求，盘点 Stream、Pending、订单和待同步记录。完整核对后再开放新入口；保留旧数据与回滚依据。演示数据重建仅适用于明确可丢弃的测试库，不默认删除现有数据库。

清理包括：Kafka 建单 relay/consumer/DLT、Kafka 专属审计与重放逻辑、Redis 延迟队列、跨服务销售库存写入、`order_inventory_operation`、订单 ShardingSphere 配置与算法依赖、旧路由基因生成路径、旧余票更新和默认迁移服务入口。异常审计能力保留并改成 Stream 来源。

不承诺未经实施验证的“一天改完”或“十至十二天完成”。以各阶段验收结果控制进度，不为了工期省略闭环或故障验证。

## 11. 验收与测量

必须可复现的五个故障场景：

1. 数据库提交后、ACK 前强制终止消费者；Pending 重领后没有重复订单、额度变化或库存副作用。
2. 交易库停机，接单暂停阈值生效；恢复后请求有明确成功、拒绝或异常审计结果。
3. Redis 同步失败，待同步记录保留；恢复后正确释放座位，旧释放不能改变新预订归属。
4. 同一 reservationId 重复投递十次，只有一笔订单；同一 userId/requestId 换预订号也不能创建第二笔。
5. 未支付订单到期后被数据库扫描关闭，座位和账号额度恢复，重复执行无额外变化。

同时验证：同座位并发争抢、多座位部分冲突整单回滚、相同请求号换参数被拒绝、支付与关单竞争、迟到消息不能复活已拒绝请求、维护重建保留已锁定和已售座位。Redis 切换需另行记录受理阶段实际数据边界。

四组测量：

- 锁座 Lua 吞吐与 P99，区分成功预占、拒绝和重试。
- 完整交易库事务耗时分布及锁等待。
- Stream 积压、最老消息年龄与 Redis 内存增长。
- 改造前后端到端 P99，统一从请求进入到明确结果持久化的口径。

报告记录相同硬件、配置、入口、场次分布、每单票数和负载模型；区分接单吞吐与订单提交吞吐。没有实测就不对外给出性能结论，不用 Lua 命令数或 batch 算式代替容量结果。

## 12. 设计摘要

完成实现与验证后，项目主线可概括为：

> Redis Lua 原子预占并写入 Stream，订单服务通过单个 MySQL 事务完成请求幂等、限购、座位锁定和建单。座位行就是库存，余票数量按需派生。后台保留消息重领、到期关单和 Redis 同步，并通过故障演练验证恢复行为。

重点讲流量准入与背压、Lua 边界、至少一次与业务幂等、数据库事务和支付状态竞争。分库分表保留为有依据的演进决策，不以中间件数量或自制恢复机制数量作为项目价值。
