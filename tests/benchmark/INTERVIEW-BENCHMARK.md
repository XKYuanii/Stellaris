# V5 自动配座：面试版压测结论

## 一句话结论

在本地单机、JMeter 与服务同机的条件下，V5 自动配座同步热路径实测峰值吞吐约 **500 TPS**；**3000 个预连接用户同时下单时 3000/3000 成功**，P99 约 6.42 秒；3500 并发开始出现连接拒绝，因此突发容量边界约为 **3000～3500 并发**。

这里的同步热路径包括：自动配座、Redis Lua 原子锁座和 Redis Stream XADD，以 HTTP 返回为结束；不把后续 Kafka 消费和 MySQL 建单时间计入响应时间。

## 测试口径

- 接口：`POST http://127.0.0.1:6086/program/order/create/v5`
- JMeter：5.6.3，Non-GUI Mode。
- 数据：独立节目 `900100`、独立票档 `900101`、10000 个座位、5000 个测试用户和5000 个观演人。
- 每个用户只发一次请求，`requestId` 唯一，不携带 Token，使用本地测试环境的 `no_verify: true`。
- 先在 10～25 秒内建立 Keep-Alive 连接，再通过 Synchronizing Timer 同时释放正式 POST，避免把同机 TCP 建联风暴误当成业务处理能力。
- 观演人缓存预热后压测，避免逐请求调用 User Service。
- 成功条件：HTTP 200、业务 `code=0`、返回唯一数字订单号。
- 每轮结束仅针对独立测试节目机械清理订单、库存和 Redis 数据，再校验座位、Stream、PEL 和 Kafka LAG 全部恢复。

## 面试时怎么回答“项目 QPS 是多少”

### 30 秒回答

> 我对 V5 自动配座下单热路径做了 JMeter Non-GUI 压测，使用 5000 个独立用户、1 万个独立座位，并提前建立 Keep-Alive 连接，避免把 TCP 建联能力混进业务结果。同步口径截止到 Redis Lua 锁座和 Stream XADD 后 HTTP 返回，不等待 Kafka/MySQL。单机本地实测峰值大约 500 TPS；3000 个用户同时下单时 100% 成功，吞吐约 458 TPS，P99 约 6.4 秒。到 3500 并发开始出现约 0.94% 的连接拒绝，所以我把突发容量边界定在 3000～3500，而不会说系统稳定支持 3500 QPS。

### 简历写法

> 基于 JMeter 5.6.3 对 V5 自动配座链路进行预连接同步突发压测，构造 5000 个独立用户与 1 万座位测试集；本地单实例峰值吞吐约 500 TPS，3000 并发下请求 100% 成功（约 458 TPS，P99 6.42s），3500 并发开始出现连接拒绝，据此定位突发容量边界为 3000～3500。

### 面试官追问“那到底是 500 QPS 还是 3000 QPS？”

> 500 TPS 是单位时间内实际完成的峰值处理速率；3000 是系统一次性接住并最终成功返回的并发请求数。3000 个请求并不是一秒完成，P99 大约 6.4 秒，所以不能称为 3000 QPS。我的结论是单机峰值吞吐约 500 TPS，同时能通过排队承接 3000 个突发请求。

## 结果解读

- 推荐作为“高并发承载”展示点：3000 并发、100% 成功、P99 6.42 秒。
- 推荐作为“峰值 QPS/TPS”回答：约 500 TPS；不要说成几千 QPS。
- 3500～4000 的失败均首先表现为 TCP 连接被拒绝，不是库存不足或业务限流，说明单机 HTTP 接入已经过载。
- 4000 档总吞吐虽接近 487 TPS，但成功率只有 96.88%，不能作为稳定容量。
- 这套结果适用于本地单实例和当前硬件/配置；生产多实例部署后需要重新测试，不能按实例数机械线性放大。
